# The Concrete Programming Language

[![CI](https://github.com/lambdaclass/concrete/actions/workflows/lean_action_ci.yml/badge.svg)](https://github.com/lambdaclass/concrete/actions/workflows/lean_action_ci.yml)
[![license](https://img.shields.io/github/license/lambdaclass/concrete)](LICENSE)

**Concrete is a fully proven systems programming language with no garbage collector, where you can
know everything a program does: what it does, what it may touch, whether it can fail or stop, and
what is proved about it.** Every unproven step is named as an explicit assumption, never silently
trusted. This states the project's goal: each guarantee holds only as its evidence lands, compiler
correctness and program correctness need separate proofs, and native claims remain conditional on
their named assumptions ([decision](docs/decisions.md#decided-project-core-statement)).

Concrete’s design requires explicit ownership, authority, failure handling and termination evidence.
R-0575 owns the per-function report of these facts, their evidence and any unresolved obligations.
The current CLI supports build and help. Per-function facts, stack reporting and project-budget
enforcement are planned. [Facts report](docs/decisions.md#decided-project-facts-report) ·
[No hidden traps](docs/decisions.md#decided-project-no-hidden-traps).

## Why Concrete?

Producing an implementation is becoming cheaper. Establishing what it must do,
what resources it may use, and why we should trust it remains difficult.

Concrete's direction is to make those obligations explicit: state the behavioral
contract, constrain ownership and authority, and attach evidence to the exact
implementation being checked. An implementation can change; the obligations it
must satisfy remain the basis for acceptance.

That requires more than matching return values. Failure, mutation, external
actions and resource behavior can matter too. The scope of each claim and its
remaining assumptions must be visible. Understanding the specification and
checking that it captures the intended task remain engineering responsibilities.

| Question | Concrete's approach |
| --- | --- |
| Who owns this resource? | Linear ownership and scoped borrowing. |
| What authority does this operation require? | Capabilities declared in signatures. |
| What behavior must this implementation preserve? | Explicit contracts and semantic obligations. |
| Why should I accept this claim? | Distinct proof, test, runtime-check and assumption evidence. |

The long-term goal is verified compilation from source to native execution,
with evidence that can be composed and independently replayed. This is a target,
not a current guarantee.

**Status: early vertical slices.** The standalone Slice 0 driver compiles a parameterless `main`
returning `u8`, with immutable typed `u8` bindings, decimal literals, reads, parentheses and checked
addition. It builds native executables through LLVM and LCB on supported hosts, subject to backend
limits. The input is a canonical project-relative `.con` file in a project without `Concrete.toml`.
Native correctness remains conditional. Slice 1 and the stage-interface cutover are in progress.
The language specification remains provisional until the Slice 11 Core freeze (`A2c`).
[Running the current slice](Concrete/README.md#running-the-current-slice).

## What Concrete learns from

| Part of Concrete | Main precedent |
|---|---|
| Linear ownership, scoped borrows, capabilities in signatures | Austral |
| Mutable value semantics: mutation through scoped access, no returned or stored references | Hylo (formerly Val) |
| A small explicit language: no hidden control flow or allocation, allocators passed as parameters | Zig |
| Compiler-enforced safety culture and an explicit trusted boundary | Rust |
| Verified compilation: source behaviour carried down to the binary | CakeML and CompCert |
| Absence of run-time errors and the assurance workflow | SPARK, with Dafny and Why3 |
| Rules and proofs in one checked system; the implementation language | Lean 4 |

Smaller influences include Aeneas and Effekt. The full comparison, including what Concrete takes
from each and what it rejects, is archived in
[legacy/docs/project/INFLUENCES.md](legacy/docs/project/INFLUENCES.md).

## The old compiler

`legacy/` is a frozen snapshot of the old tree: it is never edited and never run here. The old
compiler is tag `legacy-compiler-final`; to use it, check that tag out in its own worktree. The
differential oracle is built from the tag, not from `legacy/` (`scripts/oracle/`). Assets the new
compiler still needs (programs, examples, std, the bug ledger, the site) stay archived in `legacy/`
until they migrate; [RETENTION.tsv](RETENTION.tsv) records each one.

```sh
nix develop -c lake build                  # specification and compiler library
nix develop -c lake build concrete         # CLI executable (.lake/build/bin/concrete)
nix develop .#gates -c bash scripts/checks/run.sh
```
