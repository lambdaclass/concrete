# FFI and Unsafe Boundary

Status: stable reference

This document describes the current foreign-function interface boundary and the role of `Unsafe` in Concrete.

For the full safety model (capabilities, trusted, Unsafe, proof boundary), see [SAFETY.md](../language/SAFETY.md). For layout and representation rules, see [ABI.md](ABI.md). For active priorities, see [../ROADMAP.md](../../ROADMAP.md).

The planned package workflow for C, Rust and Zig is described in
[FFI_GLUE.md](FFI_GLUE.md): applications declare a dependency and use normal imports;
tooling generates wrappers and builds/links the native library. That automation is not
implemented yet. The declarations below describe the current language boundary. A package
names the C library its `extern fn`s resolve against in `Concrete.toml` `[native]`, and the
build links it into every program that depends on the package: see
[NATIVE_LIBRARIES.md](NATIVE_LIBRARIES.md).

## Core Principles

Concrete keeps the foreign boundary explicit:

- FFI functions are declared with `extern fn`
- raw pointers are explicit types (`*const T`, `*mut T`)
- unsafe operations are gated by `with(Unsafe)`
- safe code does not silently cross into foreign or pointer-sensitive behavior

## Extern Functions

Extern declarations are the language-level entry point to foreign code:

```con
extern fn puts(ptr: *const u8) -> i32;
```

Current rules:

- `extern fn` has no Concrete body
- extern calls require `Unsafe` by default
- extern parameter and return types must be FFI-safe

### Trusted Extern Functions

A `trusted extern fn` is an audited foreign binding that callers can use without `with(Unsafe)`:

```con
trusted extern fn sqrt(x: Float64) -> Float64;
```

This is the right tool for well-known, pure libc functions (math, `abs`, etc.) where requiring `Unsafe` at every call site adds noise without safety value.

Rules:

- `trusted extern fn` uses the existing `trusted` keyword — no new syntax
- callers do not need `with(Unsafe)`
- parameter and return types must still be FFI-safe
- the declaration itself is the audit boundary — it asserts the foreign function is safe to call with any valid arguments of the declared types
- every `extern` (trusted or not) declares its effects, `with(...)`, and `with()` for none; an undeclared binding is refused (E0116), and a known-effectful C symbol declared `with()` is refused (E0117), in every module, nested submodules included (enforced; bug 113). An `#[intrinsic = "n"]` declaration named `n` that the compiler implements (`resolveIntrinsic`) is not a foreign binding and needs no effect declaration (bug 112); any other `#[intrinsic]` annotation leaves the declaration a foreign binding under every rule. The declared effects bind every caller, trusted bodies included (R-0484)
- `--report unsafe` shows trusted extern declarations in a separate "Trusted extern functions" section

Keep the category narrow. `trusted extern fn` means "safe for every argument its types permit, with no undeclared effects" — not a general "safe FFI" escape hatch. A foreign function whose safety depends on pointer validity, or that can invalidate a resource another handle owns (`close`), stays a regular `extern fn`; its callers outside `trusted` code need `with(Unsafe)`. Effects are not what decides this: they are declared either way.

## Symbol Names (normative, decided 2026-10-21)

**Rule.**

1. Every **Concrete-defined** function — user-written, `std`, or compiler-generated
   (specializations, synthesized destructors, entry wrappers, runtime helpers such as
   `string_length`) — is emitted under a **mangled symbol in a namespace disjoint from C**, derived
   from its module path and a disambiguator taken from its resolved definition identity (`DefId`,
   R-0492). No C identifier and no user-chosen spelling can occupy it, so a Concrete function can
   never define or replace a foreign symbol by being named like one.
2. Only two forms produce an **unmangled C name**: an `extern fn` declaration (an import), and an
   explicit export attribute (the reverse direction, R-0286). The process entry symbol `main` is
   generated by the compiler and calls the program's `main` (MAIN_EXIT_MODEL.md).
3. **`#[link_name = "sym"]`** on an `extern fn` binds the C symbol `sym`, for a symbol that is not
   a legal or desired Concrete identifier. Without it, an `extern fn` binds the symbol spelled like
   its declared name.
4. A generated definition never stands in for an unresolved foreign name: a missing foreign
   function is an error, never a synthesized body. The disjoint namespace makes such a collision
   loud; it does not replace the identity-based synthesis of destructors (R-0510), which is the
   repair for bug 103's root (structural class 3).

**Status on main: enforced** (2026-10-21, bugs 129 and 103; `Concrete/Backend/Symbols.lean` is the
one place that spells a link symbol).

- Rule 1: every Concrete-defined function is emitted as `_C.<module path>.<name>` (the entry
  `main` included: `_C.main.main`, which the generated C `main` calls), and every compiler
  runtime helper (`string_*`, `print_*`, `*_to_string`, `vec_*`, `__concrete_check_oom`) as
  `_C$rt.<name>`. Every such symbol contains `.` or `$`, which no C identifier contains, so the
  namespaces are disjoint by construction: `fn malloc` is `_C.main.malloc` and `alloc` still
  calls C's `malloc` (bug 129). The disambiguator is the function's Core name (impl methods
  `Type_method`, specializations `f_for_T`, glue `$destroy$<type>`), unique per module path; it
  becomes the `DefId` when R-0492 lands. Mangling is an emission concern: Core names,
  CallableIds, proof and report identities do not change (the traceability report's `llvm:` row
  shows the mangled symbol).
- Rule 2: the only unmangled names a program defines are `#[export_name = "sym"]` functions and
  the generated C `main`. An export must be a C identifier, not `main`, not `__`-prefixed, not a C
  runtime symbol the program itself calls (`malloc`, `free`, `write`, ...), not a symbol an
  `extern fn` imports, unique, and of a C-compatible shape (not generic, not `main`, not a test,
  32- or 64-bit integer / float / raw-pointer parameters and result: 8- and 16-bit integers need
  the C ABI's sign or zero extension, which emission does not do); otherwise E0119. The header, report and
  library-output parts of R-0286 are not built yet.
- Rule 3: `#[link_name = "sym"]` on an `extern fn` binds `sym` (ASCII letters, digits, `_`, `$`,
  `.`; never in the `_C.` / `_C$` namespace; E0118). A foreign binding's identity is its name
  (`CallableId.ofExtern`), so one name binds one C symbol across the program (two declarations
  of `f` with different link names: E0118), and no binding may name a compiler runtime helper
  (`print_int`, `string_length`, `vec_*`, ...; E0118), which emission renames into `_C$rt.`, nor
  be spelled like a compiler intrinsic (`sizeof`, ...; E0118), since such a call is compiled as
  the intrinsic and never reaches C (`free` and `abort` without a link name excepted: their
  intrinsics are those C functions); likewise no import may be renamed to an intrinsic's name
  (`import c.{abs as sizeof}`, E0120). A call the resolver binds to a runtime-helper intrinsic
  carries the helper's `_C$rt.` symbol into emission, so another module's Concrete function of
  that name cannot capture it.
  R-0484 R3's effectful-symbol check (E0117) judges the C symbol the binding calls. Every call the
  resolver binds to an extern, own or imported, carries that binding to emission
  (`CFnDef.foreignCalls`), so it calls the C symbol even when some module defines a Concrete
  function of the same spelling.
- Rule 4: the compiler's own C calls (`alloc` → `malloc`, `free`) are `SCallee.foreign` and are
  never resolved against Concrete definitions; destructors are dispatched by type through the
  reserved `$destroy` callee (bug 103, fixed on main by `0c507fb9`), and their glue is mangled too.
- Open: a foreign function taken as a VALUE is called with the Concrete ABI, so a small
  `#[repr(C)]` struct argument reaches C as a pointer (bug 166, predates this work; owner R-0283).
- Open: a call Elab GENERATES (`println` → `print_int`) still binds by spelling, so a module
  defining its own `print_int` captures it (bug 165, predates mangling; owner R-0492).
- Not mangled: the runtime ABI symbols std imports through `extern fn` (`__concrete_get_argc`,
  `__concrete_get_argv`, the `__concrete_argc`/`__concrete_argv` globals) and the `internal`
  checked-arithmetic helpers (`__cc_*`); the `__` prefix is reserved to the implementation in C
  and refused for Concrete definitions (bug 028).

**Prevents.** Bug 103's silent replacement (made loud), bug 028's class, and the user-function
capture of a C symbol ([bug 129](../bugs/129_user_fn_captures_libc_symbol.md): a safe function
named like a libc symbol replaces it program-wide).

**Migration.** No source change. Mangling changes what tools see: the program's `main` is
`_C.main.main` (formerly `user_main`), profiler and debugger tooling show `_C.` symbols, and tests
that assert `@name` in `--emit-llvm` output now match `@_C.<module>.<name>`
(`check_fnptr_values.sh`, `check_trap_inventory.sh`, `check_indirect_call_identity.sh`,
`check_collections_copy_only.sh`, run_tests.sh traceability). A C program that called a Concrete
function by its bare name must export it with `#[export_name]`.

**Owners.** Bugs 103 and 129: ROADMAP exit 0b (R-0482), as wrong code and a
memory-safety defect in safe code. Mangling and the namespace: R-0285 / R-0283 (the foreign
boundary), with R-0510 for generated symbols; the export attribute: R-0286.

## Foreign Function Values (normative, decided 2026-10-23)

The C calling convention is decided at a direct call of a foreign function: a `#[repr(C)]`
aggregate is flattened into registers the way C declares it. A function type (`fn(P) -> R`)
carries no calling convention, so a call through a function value always uses the Concrete one.
Taking as a value an `extern fn` whose signature has a `#[repr(C)]` struct among its parameters or
as its result is therefore refused (E0588, bug 166). A foreign function without such an aggregate
has one ABI and may be used as a value. To pass such a function, pass a Concrete function whose
body calls it directly.

Design note, not adopted: a calling convention carried in the function type (`extern "C" fn(P) ->
R`), with a mismatch refused, would let a foreign function be a value and would also type C
callbacks. It waits for a workload that passes such a function to C or stores one
([TIGHTENING_DECISIONS](../language/TIGHTENING_DECISIONS.md) Q4).

## FFI-Safe Types

FFI-safe types currently include:

- integer types
- float types
- `Bool`
- `Char`
- `()`
- raw pointers (`*const T`, `*mut T`)
- `#[repr(C)]` structs

The implementation authority for this check is `Layout.isFFISafe`.

## Unsafe Boundary

Concrete currently requires `Unsafe` for:

- calling `extern fn` (but not `trusted extern fn`)
- dereferencing raw pointers
- assigning through raw pointers
- pointer-involving casts, except reference-to-pointer casts

Safe exception:

- `&x as *const T`
- `&mut x as *mut T`

These preserve compiler-known provenance and do not invent an address.

## Intentional Design Rule

The goal is not to hide low-level operations behind “safe-feeling” library APIs.

The audit story should stay simple:

- `grep with(Unsafe)` finds the boundary
- extern declarations are visible in signatures
- raw pointers stay explicit in types

Concrete is aiming for an unsafe boundary that is:

- operationally obvious
- explicitly gated
- easier to audit than a broad ambient low-level model

## Trusted Split

Concrete now has the three-way split described in the research notes:

- **capabilities** (`with(Alloc)`, `with(File)`, etc.) = semantic effects visible to callers
- **`trusted`** = containment of internal pointer-level implementation techniques behind a safe API
- **`with(Unsafe)`** = the memory-safety obligation of crossing a foreign boundary (FFI, transmute) — explicit in every signature that is not `trusted`; a `trusted` body absorbs it (R-0484)

That means:

- `trusted` does **not** suppress ordinary capabilities
- `trusted fn`/`trusted impl` absorbs the `Unsafe` of an `extern fn` call (since R-0484, 2026-10-01) — never the binding's declared effects, which every `extern` must state
- `trusted extern fn` is a separate, narrower mechanism: it marks a specific foreign binding as safe to call, rather than granting blanket trust to a block of code
- builtin and stdlib internals are aligned to this same model instead of relying on silent exemptions

## Authority Wrapper Patterns

The recommended pattern for containing unsafe or capability-requiring code is: write a small trusted wrapper, expose a safe narrow interface above it, keep raw pointers and FFI details inside the wrapper.

```con
// Bad: callers need with(Unsafe) to use raw FFI
pub fn read_header(fd: i32) with(Unsafe) -> Int {
    // raw extern call ...
}

// Good: trusted wrapper contains the unsafety
pub trusted fn read_header(fd: i32) with(File, Unsafe) -> Int {
    // raw extern call inside trusted boundary
}
// Callers still need with(File, Unsafe); trusted contains the pointer work, not the capability
```

The stdlib demonstrates this pattern throughout:

- `trusted impl Vec<T>` wraps pointer arithmetic behind safe push/pop/get
- `trusted impl HashMap<K, V>` wraps raw allocation behind safe insert/get/remove
- `trusted impl TextFile` wraps POSIX file I/O behind open/read/write/close
- `trusted fn print/println` wraps extern console I/O behind `with(Console)`
- `trusted extern fn sqrt` marks a pure foreign function as safe to call without `with(Unsafe)`

The `--report unsafe` and `--report authority` modes make these boundaries visible for audit.

## Capability Aliases

Capability aliases reduce signature repetition without hiding authority:

```con pseudocode
cap IO = File + Console;
cap Host = File + Network + Env + Process;

fn serve() with(Host) -> Int { ... }
fn log(msg: &String) with(IO) { ... }
```

An alias expands to its constituent capabilities at parse time — the rest of the compiler sees only concrete capability names. Aliases can use the fixed `Std` capability alias (`cap All = Std;` expands to all standard capabilities except `Unsafe`). This is not a macro system.

Aliases are validated at definition time: all constituent names must be known capabilities. Unknown names produce a parse error.
