# Landing trains

Status: operational procedure (ROADMAP R-0539, measurement R-0547)

Ready branches land together as one **train**: one integrated candidate, one CI run, and
bisection by member only when that run is red. `scripts/land/train.sh` does what an orchestrator
used to do by hand, and refuses the mistakes that hand-run trains made on 2026-10-22.

## The cycle

```sh
scripts/land/train.sh build  <name> <ref>...   # train/<name> = origin/main + each ref, --no-ff, in order
scripts/land/train.sh check  <name>            # fast surface + impact-selected gates on the gate host (+ remote full set)
scripts/land/train.sh ci     <name>            # push ci/<name>, dispatch CI, record the run id
scripts/land/train.sh watch  <name>            # poll to a verdict; failing jobs' log tails
scripts/land/train.sh land   <name>            # verify, then push the exact SHA to origin main
scripts/land/report.sh                         # median time to land, per-stage medians
```

`--dry-run` before the subcommand prints pushes, dispatches and the remote run instead of doing
them. `land --dry-run` still performs every verification, so it is the way to ask "would this land?".
`train.sh status <name>` prints the train's state and log.

**Where a train runs.** Only in a full clone (`git clone`) whose pre-push hook is the repository's
(`git config core.hooksPath .githooks`, or a wrapper hook that runs `.githooks/pre-push`, like
`acceptance.sh`'s guard). Every subcommand except `status` and `record` (which push nothing) refuses a linked worktree and a clone
with the hook off, and the hook itself refuses a gated push (anything beyond the `wip/*` and review-
notes tiers) from a linked worktree. The reason is ISS-0015: git hands a worktree's hooks
`GIT_DIR=<repo>/.git/worktrees/<name>`, and a check run under it once wrote its sandbox's branches
and test notes into a real clone and onto GitHub. Scripts that make throwaway repositories clear
git's repository variables through `scripts/checks/lib/git_sandbox.sh` (checked by
`scripts/checks/sandbox_isolation.sh`), so the refusals are a second wall, not the only one.

### build

- Creates `train/<name>` from `origin/main` (after a fetch) and merges each ref with `--no-ff`.
  The merge message names the member and its SHA. A ref that is already in main is skipped.
- `--force` rebuilds an existing train. That is the normal response to a moved main.
- Conflicts are resolved mechanically only in three kinds of file
  (`scripts/land/resolve_conflicts.py`):

  | kind | files | resolution |
  |---|---|---|
  | append-only ledgers | `CHANGELOG.md`, `scripts/tests/audit_bug_corpus.sh`, `docs/bugs/discovery.tsv`, `docs/project/candidates.tsv` | union of both sides' lines, only when both sides inserted lines (the diff3 base of every hunk is empty); in the corpus, only map entries inside a `declare -A` map |
  | whole generated files | `Concrete/BuildIdentity.lean` | regenerated on the train |
  | generated blocks | any file whose every conflict hunk is inside a `BEGIN GENERATED ... (scripts/gen/<generator>; ...)` block whose generator the train will run | regenerated on the train |

  A generated view is resolved only when its generator is in the regeneration plan that runs after
  the last merge. A generator that merely exists is not enough. Any other conflict, including prose
  next to a generated block and two edits of one ledger line, aborts that merge. The script
  names the files and exits 3. The train keeps the members merged before it.
- After every merge, `resolve_conflicts.py corpus-keys` refuses a duplicate key in the corpus maps,
  and a bug listed in both `BUG_TEST_MAP` and `SKIP_BUGS`. bash keeps the last of two equal keys
  without a word, and a union merge left stale OPEN entries for fixed bugs on 2026-10-22.
- After the last merge the generated views are regenerated once:
  `scripts/gen/refresh_generated.sh` when it exists (branch `ledgers`, R-0542), otherwise
  `bug_dashboard.py --write`, `candidate_table.py --write` and `build_identity.sh`, each when present.
  Any change becomes one `regenerate generated views` commit. A generator's refusal stops the build.
- After every git operation the script checks for `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`
  and a rebase in progress, and stops if one exists. It never continues past a stopped operation.
  A dirty tree is refused before anything starts.

### check

`check` runs up to three independent **legs at the same time** and collects every one before the
verdict; any failing leg fails the check (see [Pipelining](#pipelining)).

- **impact** (`scripts/land/impact_gates.sh`): runs the pre-push hook's own selection (the R-0022 fast surface gates plus the touched areas)
  over exactly the range the `ci` push will present: `train/<name>` at `base..head` on `ci/<name>`.
  The root hook writes no validation record, so the `ci` push runs its own checks again (the
  full root set); this leg is the early verdict, not a substitute for the push. With a gate host configured, this leg runs **there**
  (see [Gate host](#gate-host)).
- If `scripts/tests/select_gates.sh` (R-0513) exists and the hook does not already call it, its
  output is run as well. The interface is `select_gates.sh --base <sha> --head <sha>`, printing one
  gate command per line, which runs through `run_ci_gates_local.sh --first`.
- **remote**: the full gate set (R-0541) through `LAND_REMOTE_RUNNER <ref> <command>`. The
  default runner is `~/bin/concrete-remote`; on the server it is `scripts/land/run-at-ref.sh`, which
  runs in a fresh `clone --local`, not a worktree, because some gates refuse linked worktrees. A
  runner that fetches from origin first gets the head published under a ref unique to that run,
  `wip/land-<name>-<sha>-<pid>-<n>` (the hook's backup tier). It is created only if absent. The
  push carries an empty lease, and ownership is taken only from `--porcelain`'s `*` (new ref)
  line, because git reports an existing ref at the same SHA as up to date before it checks the
  lease. On a collision the run tries a fresh name. The ref is deleted afterwards with a lease on
  that SHA, in one attempt that is never retried. A failed push may still have deleted it, so an
  unconfirmed deletion is reported and left alone. An EXIT backstop covers interruption before
  that attempt. As a result,
  concurrent checks never share or delete each other's refs. The run counts only if the runner reports
  `sha=<head>`. `--no-remote` skips this leg.
- **review** (fails closed): the leg passes at once when the train already has **review
  provenance**: a clean review note at its head or, when the head has no note, a clean note on every
  member at its exact recorded SHA (each member was reviewed at its own head). Each note is judged by
  `scripts/review/verify.sh` on origin's notes; an absent, malformed, blocked or findings note
  qualifies nothing, and a head note that is not clean is not overridden by the members. A member
  without a clean note qualifies instead by an **owner sign-off** at its exact SHA (R-0618: a branch
  at the review-round cap of its diff's class, approved by the owner after Codex, Kimi and agy all
  reviewed that commit; `scripts/land/signoff.sh verify --base`, on origin's `refs/owner-signoff/*`). A sign-off approves that
  commit only, so a train with a signed-off member must be exactly the clean merge of its members
  onto its base: one conflict-free merge per member and nothing else. Otherwise
  the leg runs `LAND_REVIEW_CMD`, else `scripts/review/review.sh`, with `--base --head`, and then
  requires provenance: a non-zero exit fails, and so does a zero exit that leaves no clean note at the
  head. With no review command at all, `check` fails; it never disables the leg silently.
  `--no-review` skips the leg explicitly, and `land` still requires review provenance. A review that refuses a patch recording an owner
  decision is answered in the review ([REVIEW.md](REVIEW.md#owner-decisions-choosing-versus-recording)),
  never by `--no-review`.
- The per-leg durations, the wall time and their sum go to the log as a `check-legs` row.
- Runs inside `nix develop` unless already in the dev shell. `LAND_NO_NIX=1` disables this.

### ci

- Refuses unless `check` passed at this exact HEAD. Each `check` run first withdraws the previous
  pass, so a failed re-check leaves no pass behind. `--skip-check` overrides that, and the log
  records the check as `skipped`.
- Pushes in two steps:
  1. `ci/<name>` is reset to the train's base. The base is main's own commit and has already been
     published, so this push skips the hook.
  2. The train is pushed on top with the hook running. The root hook builds the spec and runs
     the full root set; it reuses no record written by `check`. The push is verified (see [Verified pushes](#verified-pushes)).

  Without the first step, a new branch has no remote base and the hook would select gates by
  diffing the whole tree.
- Dispatches `gh workflow run CI -R lambdaclass/concrete --ref ci/<name> -f
  base=<base>`. The base-sensitive checks compare with the train's base, and the run's title records
  it (`ci/<name> at base <sha>`), which main's Landing record requires (see `land`). It finds the
  run whose head SHA is the train's, records the run id and prints the run URL.

### watch

Polls until the run completes. A timeout is reported as `incomplete`, never as a result. The
command then lists every job that did not succeed, by tier, and prints the log tail of each failed
job (`gh api repos/<repo>/actions/jobs/<id>/logs`).

A run at another SHA, or a run with no landing-tier jobs, is no verdict: `watch` exits 1 and logs
`refused`.

**Campaign-only failure.** The campaign tier is the mutation campaign, the fuzz campaign and the
proof replay (`LAND_CAMPAIGN_JOBS`). When it is the only part that failed, `watch` says so and
exits 0: the campaign gates stage (c) qualification, not merges. The failure is still printed and
logged.

### land

`land` takes the same repository-wide lock as `push-both.sh` first, then checks every condition below
before anything is pushed:

- the CI run's `headSha` is the local HEAD, and the run is completed;
- every landing-tier job concluded `success`, and a run with no landing-tier jobs is refused;
- `origin/main`, read with `ls-remote`, is still the train's base;
- the train has review provenance (as in `check`'s review leg), read again from origin's notes
  rather than trusted from `check`: a check run with `--no-review` lands only on a clean note at the
  train head or, when the head has none, clean notes on every member;
- a legacy/ move candidate (a change under `legacy/`, a `legacy` that is not a directory, or a change
  to the set of top-level entries `scripts/checks/root_inventory.txt` lists; comments, order and
  nested `docs/...` or `scripts/...` entries do not count) has an accepted rehearsal of its exact
  tree on its base (`scripts/land/acceptance.sh`; the move gate in `train.sh`).

If main moved, the command exits 4 and prints the rebuild command. The result described a
candidate that no longer integrates main, so the train is rebuilt, checked and run again.

The push sequence:

1. Pushes the exact SHA to `origin main` through the hook, which runs the full root set again. main
   is **never force-pushed**, not even with a lease. A plain push is a fast-forward or a refusal,
   so a publisher that moved main without taking the lock makes the push fail. Nothing it pushed
   is undone.
2. Checks `origin/main` with `ls-remote` once more; the landing is complete only when it is at the
   head. There is no mirror: lambdaclass/concrete is the one repository by the owner's decision of
   2026-11-06, pending its record in `docs/decisions.md`, and `origin` is it in every clone.
3. Cancels nothing. The push to main starts CI on main at the landed SHA, and that run's first job,
   **Landing record**, runs `train.sh record <head> --base <before>` (R-0570). It finds the newest
   completed `workflow_dispatch` run of CI at exactly that SHA whose title says it ran at base
   `<before>`: `ci` dispatches with `-f base=<train base>`, the workflow's `run-name` writes
   `<ref> at base <sha>`, and the base-sensitive checks (`LL1_BASE`, `TOTALITY_BASE`,
   `CONFORMANCE_BASE`, `SPEC_BASE`) compare with that base as a push to main compares with the
   previous main. It checks that run under `land`'s own rule: every landing-tier job and every
   required job succeeded, with the required set computed from the SHA main had before the push,
   and the head strictly ahead of it. When the record holds, main's run skips every other job and concludes success, and
   its summary links the qualifying run. When it does not (a hand push, a run at another SHA, a
   skipped, cancelled or failed job, an unreadable API), nothing is skipped and main's run runs
   every job itself. So main shows green only on a result at its exact SHA, and a landing still
   costs one full run. Confirm with `gh run list --workflow CI --branch main`.

#### Verified pushes

A push's exit status is not its result. GitHub drops the connection during a long pre-push hook, so
a push can fail after the remote moved, or before. The train's push to `ci/<name>` and the push
of `land` are followed by an `ls-remote` of the ref: at the head, it is done, whatever git reported; still at its old value, it is
retried (`LAND_PUSH_ATTEMPTS`, default 3, `LAND_PUSH_RETRY_SLEEP` seconds apart); moved to anything
else, it stops at once. A retry to main is still a plain push, a fast-forward or a refusal, and the
hook runs the full root set again. The reset of `ci/<name>` to the base skips the hook and is
not retried; a failure there stops `ci` before anything is dispatched.

A remote named `fork` is refused. There is no mirror or `--no-mirror` option. `push-both.sh`, the
by-hand publisher, likewise pushes only origin.

### bisect

```sh
scripts/land/train.sh bisect <name> --test '<command that fails on the red train>'
scripts/land/train.sh bisect <name> --ci        # each subset through check, ci and watch
```

Halves the member list until one member remains. Each subset is its own train (`<name>-b<k>`),
built from the members' recorded SHAs. Its result is logged against that train's head. The suspect
is then built alone. If it is green alone, the failure is an interaction between members and the
report says so. The command prints the rebuild without the culprit. A member removed by bisection
keeps the failure attributed to it.

### Gate host

Heavy legs run on the CI server, not on the machine that pushes. The pushing machine keeps the
credentials, and the gate host (concrete-ci-2) does the compute. The gate host is `LAND_GATES_HOST`
when set (empty means none), else `git config land.gatesHost`. Set it once per clone, for example
`git config land.gatesHost concrete-ci-2`, where `concrete-ci-2` is an ssh destination from
`~/.ssh/config`.

With a gate host, `check`'s impact leg is `scripts/land/gates_remote.sh`:

1. It bundles `base..head` under a temporary ref.
2. The transport (`scripts/land/gates_transport_ssh.sh`) copies one directory to the host: the
   bundle, this checkout's `run-at-ref.sh`, and a script that quotes the command for bash. The
   host's login shell sees only `bash land-remote-<id>/run.sh`. That script runs `git fetch origin`
   in the host's gate clone (`~/concrete2`, a path name only: its origin is lambdaclass/concrete), runs `run-at-ref.sh` on the bundle, and removes the
   directory. The host therefore needs no GitHub credentials and no copy of the landing scripts.
3. In a fresh clone of exactly the head, the host runs `impact_gates.sh`: the same hook, with the
   same input line the `ci` push will present. The command first unsets `CONCRETE_SKIP_GATES`
   (whatever the host's environment holds) and the hook's re-entry marker. Then it exports this
   checkout's `CONCRETE_*` variables, NUL-delimited, with validated names and `%q`-quoted values.

The verdict comes from the log, bound to the SHA. The log must hold exactly one start line and one
exit line from `run-at-ref.sh`, and both must name the head.

| result | exit | effect |
|---|---|---|
| passed at the head | 0 | the leg passes |
| gates failed at the head | 1 | the check fails |
| run at another SHA, unreachable host, lost connection, log missing either line | 3 | **INCOMPLETE**: the check fails and the log records `check incomplete` |

INCOMPLETE is never a pass. It does not fall back to running the gates here. With a gate host
configured, running them on this machine takes the explicit `train.sh check <name> --local-gates`.
A clone with no gate host (CI, the landing gate's sandbox, a clone on the gate host itself)
runs them here, says so, and logs `impact here`.

**Reuse at the `ci` push.** The root hook (`.githooks/pre-push`) writes no validation record and
never consults an attestation, so at the root no push skips its checks. What follows describes the
mechanism for a hook that writes one (the archived legacy hook): when the host's hook wrote a validation record, the log carries it
between `=== concrete-remote-record-begin` / `-end` markers. On a pass, the train worktree keeps two
files in its git directory:

- the log, at `concrete-prepush-remote-record.log`;
- an attestation, at `concrete-prepush-remote-record`.

The attestation records the head, the host, the log's digest and `complete=1`.

The pre-push hook stays the enforcement point. It skips its own run **only** when all of these hold:

- the attestation is complete and names this HEAD;
- the log's digest matches the one attested;
- the log shows exit 0 at this SHA;
- the embedded record is complete and a pass;
- every host-independent component equals this push's. These are the commit and every pushed
  ref, `lean-toolchain`, the committed gate definitions, the resolved selection, the changed-file
  list, the fuzz seed and the `CONCRETE_*` environment. The tracked tree must also be clean.

Host-specific components (compiler binary, lean, cc) describe the host and are not compared. If any
check fails, the hook names the reason and runs the gates here. If the host passed but wrote no
record, the leg passes and says that the push will run the gates locally.

Each run of `gates_remote.sh`, and each `check`, first removes the previous attestation. The attestation and its log are files in the git
directory, like the local record. They catch mismatches, truncation and digest-breaking edits. They
are not a signature against someone who can write the git directory.

## Where the record lives (R-0547)

Every subcommand appends one row to the train's log:

- the time in UTC;
- the train, stage, base and head;
- the members, as `ref@sha`;
- the run id, result and duration;
- a note.

Results use the promotion pipeline's vocabulary:

- `passed`, `failed` and `skipped`;
- `incomplete` for no verdict;
- `refused` and `conflict` for a refusal by the script.

**Decision: the log is kept local, one file per train, in the git common directory**
(`<git-common-dir>/concrete-landing/log/<train>.tsv`). Train state lives next to it, in
`<train>/train.env`. The reasons:

- **Committing it to the train changes the candidate.** A row appended to the train after CI ran
  would land a SHA that CI never validated. The `land` row cannot exist before the land happens.
- **One shared TSV conflicts.** Every train would append to the same file, which recreates the
  ledger conflicts R-0542 removes. One file per train cannot conflict.
- **The common directory is shared by every worktree.** `report.sh` and `train.sh status` see every
  train of the clone from any of its worktrees; building, checking and landing run only in the full
  clone itself ("Where a train runs").

To publish the record, `report.sh --export docs/project/landing_log/` copies the per-train files
into the tree for a documentation-only commit. Per-train files never conflict on rebase. That
directory is what R-0547's generated median, next to the candidate table, will read.

## Readiness

A branch is **ready** when all of the following hold:

- it is on origin, named `wip/<name>`;
- its head commit is not in main;
- its head carries both notes below, published on origin.

| notes ref | lines | writer |
|---|---|---|
| `refs/notes/concrete-review` | `verdict: clean\|findings\|blocked`, `rounds: N`, `reviewer: codex`, `utc: ...`, `base: <sha>`, `pieces: N` | `scripts/review/review.sh` (`scripts/review/verify.sh` reads it) |
| `refs/notes/concrete-gates` | `gates: pass\|fail`, `selected: N`, `utc: ...` | `scripts/land/ready.sh` |

One `key: value` per line; when a key repeats, the last line wins. `scripts/land/notes.sh` reads and
writes the notes (`get`, `put`, `ready`). `put` builds each write on its own temporary ref on top
of the remote's notes tip, pushes that commit without force, and retries on a race. Concurrent
writers therefore never drop each other's notes, including writers that share one clone or its
worktrees.

**Decision: candidates are `wip/*` branches whose head carries both notes. There is no `ready/*`
prefix.** The reasons:

- **A note is bound to a commit.** A new push starts with no notes, so "ready at the exact head"
  needs no extra rule, and no ready branch can go stale.
- **Agents already push `wip/*`.** The pre-push hook's backup tier keeps those pushes cheap, and
  marking a branch ready is a metadata write, not another branch to keep in step.
- **The ready list is a query**, so nothing has to be cleaned up after a landing.

`wip/land-*` is reserved for the remote leg's temporary refs and is never a candidate.

To mark a branch ready, push it, then run `scripts/land/ready.sh wip/<name>` from a clean
checkout at its head. It runs the review, the impact gates and the remote full set in parallel,
then publishes the gates note: `gates: pass` only when every leg that ran passed. A failed review
leg also publishes `gates: fail`, so an older clean verdict cannot keep the head ready. It exits 0
when the head is ready.

## Pipelining

The review, the impact gates and the remote full set do not depend on each other. `ready.sh` and
`train.sh check` therefore start all three together and wait for all of them. The wall time
becomes the slowest leg instead of the sum. Both scripts record each leg's duration, the wall time
and the sum: `ready.sh` in `<git-common-dir>/concrete-landing/ready.tsv`, and `check` as the
`check-legs` row of the train log.

**Measured on 2026-10-22, on branch `wip/landing-bot`.** Two runs of `ready.sh`, each with its legs
started together:

| run | review (Codex) | impact | remote full set | wall | one after another |
|---|---|---|---|---|---|
| laptop, `f55935ac` | 117 s | 51 s | lost when the laptop lost its network | n/a | n/a |
| concrete-ci-1, `93aa7ac5` | not run (no Codex login for `dev`) | 69 s | 5239 s, red | 5239 s | 5308 s |

The server was shared with other full runs at a load average of 15 to 32.

- **Saving.** The impact gates (69 s) and the review (117 s, from the laptop run) finish inside the
  remote leg, so about 3 minutes come off every readiness check. Measured: 69 s with the impact
  leg alone, and 186 s with the review included.
- **What dominates.** The remote full set is about 98% of the cost: 87 minutes on a loaded host.
  Pipelining removes the queue in front of it, not the leg itself. The next lever is the full
  set's own time (R-0546 caches, R-0541 dedicated runners) and keeping concurrent full runs off
  the same host.
- **Why the remote leg was red.** Five gates failed:
  - `check_phase6c_observability.sh` #5 and `check_campaign_summary_golden.sh` refuse to run in a
    linked worktree ("Run it in a clone"), which is how that run was made. `run-at-ref.sh` now
    uses `clone --local`.
  - `check_example_outputs.sh` under valgrind, `run_tests.sh` and `check_external_checker.sh`
    were not examined.

  This branch changes only `scripts/land`, one build-free gate with its registration, and this
  document. CI on a train is where those three would be settled.
- **Not counted.** Before pipelining, a human orchestrator usually started the review, the impact
  gates and the remote set by hand in sequence, and each hand-off waited for someone to notice
  the previous result. The scripts remove that wait, and this table does not measure it.

`scripts/checks/landing_script.sh` runs in CI's build-free grammar job. It drives the real
script against a throwaway repository with bare-repo remotes and a fake `gh`. It covers:

- every resolution route;
- every refusal: a real conflict, prose next to a generated block, a duplicate corpus key, a merge
  or rebase already in progress, a dirty tree, an existing train, a head-SHA mismatch, a red
  landing job, a moved main and a remote named `fork`;
- the check → ci → watch → land pipeline, with both dry-runs;
- one repository: with no `lambdaclass` remote configured, `land` succeeds and its exact push log is
  one push to origin; `ci` defaults `LAND_REPO` to lambdaclass/concrete; `push-both.sh` makes exactly
  one push and reports its destination;
- `ci` dispatches with the train's base; `land` cancels no run; `record` names the qualifying run
  only for the newest completed dispatch of CI at exactly the head and the base with every
  landing-tier and required job green, and refuses each of: no run, a run at another SHA or base, a
  push, pull-request or base-less dispatch, another workflow, an unfinished run or the asking run
  itself, a skipped, cancelled or failed job, an older green run behind a newer red one, a head not
  strictly ahead of the base, an absent or all-zero base and unreadable APIs; and the workflow gates
  every landing-tier job on the record and every base-sensitive check on the dispatch's base (with
  controls for an ungated job, a dependent forced by `always()`, a gate without `!cancelled()` and
  a check that ignores the base);
- verified pushes: a push dropped before the remote moved is retried, one dropped after it moved is
  accepted from `ls-remote`, and exhausted retries fail without moving main;
- the gate host: a result bound to the train head's SHA. A run at another SHA, an unreachable
  host and a lost log are each INCOMPLETE and block. A failure at the head fails. `--local-gates`
  and `land.gatesHost` work as described. `run-at-ref.sh` runs a bundled head. The hook's library
  reuses an attestation only for this exact push and refuses each of the following: another SHA,
  changed files, selection or environment, a dirty tree, a tampered or re-digested log, a tampered
  or truncated attestation, and a log that is not a pass;
- bisection;
- the report.

`scripts/checks/landing_ready.sh` runs in the same job. It drives the real `ready.sh` and
`train.sh` against a throwaway repository with bare-repo remotes, a fake `gh`, a fake remote runner
and a fake hook that fails exactly when the checkout contains `BAD`. It covers:

- the remote leg: an existing ref at the candidate's SHA is refused, not adopted; the runner runs
  once, on a fresh `wip/land-*` ref, and only the run's own ref is deleted;
- `bisect --ci`: a member whose CI is red is named, each probe dispatching its own run, and nothing
  lands;
- `ready.sh`: a failed review leg publishing `gates: fail` over an older clean verdict, and
  passing legs making a head ready;
- a static check that nothing under `scripts/land` force-pushes main.
# Self-hosted CI runners

The CI workflow (`.github/workflows/lean_action_ci.yml`) and the branch-health workflow can run
their Ubuntu jobs on our own servers instead of GitHub-hosted `ubuntu-latest`. This page covers what
the switch does, how to set up a server, and the security rules for a **public** repository.

## What the switch does

Every Ubuntu job's `runs-on` is:

```yaml
runs-on: ${{ (github.event_name != 'pull_request' && vars.CONCRETE_SELF_HOSTED == 'true') && fromJSON('["self-hosted","linux","x64","concrete"]') || 'ubuntu-latest' }}
```

- The repository variable `CONCRETE_SELF_HOSTED` routes the **landing tier** (build, test suites,
  trust, proof and evidence jobs, the language-surface jobs, multi-kernel) and branch health.
- `CONCRETE_SELF_HOSTED_CAMPAIGN` routes the **campaign tier** (mutation plan, the 24 mutation
  shards, the aggregate, the fuzz campaign, the proof replay) on its own, and the two light jobs of
  the nightly workflow (`nightly.yml`: the dispatch and the report, which need `gh` and `python3`). Leave it unset
  unless the servers can absorb 24 shards of up to ~85 minutes each. Labels give no priority, so a
  campaign on self-hosted runners would queue landing runs behind it.
  The tiers are listed in [PROMOTION_PIPELINE.md](../legacy/docs/project/PROMOTION_PIPELINE.md#ci-tiers).
- An unset variable, or any value other than `true`, means GitHub-hosted. That is the default.
- **A `pull_request` event never runs on a self-hosted runner**, whatever the variables say. See
  the security section for why this guard alone is not enough.
- `Build + main tests (macOS)` stays on `macos-latest`. The Pages workflow (`book.yml`) stays on
  GitHub-hosted runners.

**Two pools.** CI's jobs ask for the label `concrete`; branch health asks for `concrete-light`, a
separate pool of small runners (two on concrete-ci-2, `LIGHT_RUNNERS` in the dotfiles host file).
Branch health runs on every push to every branch, about 500 runs a day, and on the `concrete` pool
those runs took 20-92 runner-minutes out of each train's window (measured 2026-10-24). Labels give
no priority, so the only way to keep a train from queueing behind them is to not share the pool.
A `concrete-light` runner carries only that label, so CI never lands on it either.

### Runner pools and their limits (P13, owner-approved 2026-11-05)

CI runs on two regular pools: concrete-ci-2's self-hosted runners and GitHub-hosted runners. Neither
is a fallback that weakens a check; each required check runs on a pool that can run it, or is
INCOMPLETE and blocks the landing.

| Pool | Where | Limits (set 2026-11-06) | Runs |
|---|---|---|---|
| `concrete` | concrete-ci-2 (Hetzner AX102: 32 threads, 125 GB RAM) | 6 runners `gha1`..`gha6`, so at most 6 concurrent jobs; each has `MemoryMax=28G` and no swap, and no per-runner CPU cap | the landing tier when `CONCRETE_SELF_HOSTED=true`; never a `pull_request` |
| `concrete-light` | concrete-ci-2 | 2 runners `gha7`, `gha8` (`LIGHT_RUNNERS` in the dotfiles host file), each `CPUQuota=400%` and `MemoryMax=8G` | branch health only |
| GitHub-hosted | `ubuntu-latest`, `macos-latest` | GitHub's per-repository concurrency | every landing-tier job when the variable is off; always: `Oracle (GitHub-hosted fetch + smoke)` and `Build + main tests (macOS)`; every `pull_request` |

Both pools on concrete-ci-2 run inside `concrete-runners.slice`, capped together at `CPUQuota=2400%`
(24 of 32 threads), `MemoryMax=96G`, no swap and `TasksMax=16384` (ISS-0007, applied 2026-11-06).
The runners together can therefore never use more than 24 CPU-equivalents or 96 GB, which leaves
8 CPU-equivalents and about 25 GB of headroom for gate runs, agents and logins in `user.slice`. This is
headroom, not a reservation: those processes share it, and only `system.slice`'s 4 GB `MemoryMin` (sshd,
tailscaled) is reserved. The slice keeps the default CPU weight (100) against
`user.slice`'s 25, so CI still wins under contention. There is no `MemoryHigh`: a job past its
`MemoryMax` is killed inside the slice rather than throttled. The values live in the dotfiles host
file (`servers/hosts/concrete-ci-2.env`, `CONCRETE_RUNNERS_*` and `CONCRETE_*RUNNER_*`), and
`servers/runners.sh` writes them, so a rebuilt host gets the same caps.

Manual heavy work on concrete-ci-2 (train check legs through `land.gatesHost`, `run-at-ref.sh`
runs, oracle rebuilds) follows the machine-wide rule: at most two full suites, mutation campaigns
or other CPU-heavy checks at once (AGENTS.md, ROADMAP R-0543).

**What runs where on the GitHub-hosted pool.** Every landing-tier job's `runs-on` falls back to
`ubuntu-latest`, so the whole landing tier can run there; the only self-hosted-only steps are cache
seeding (`Seed .lake from the server build cache`), whose absence means a cold build, never a
skipped check. The oracle differential gets its oracle on a GitHub-hosted runner from the published
release (`scripts/oracle/fetch.sh`: the lock's artifact sha256, install manifest and binary hash);
`scripts/oracle/ci_check.sh` reports a missing, corrupted or unverifiable artifact as INCOMPLETE
(exit 3), which fails the required job (`scripts/checks/oracle_fetch.sh` holds this). The
oracle rebuild (`oracle.yml`, weekly) runs on either pool.

A job routed to self-hosted waits until a runner with **all four** labels `self-hosted`, `linux`,
`x64` and its pool label (`concrete`, or `concrete-light` for branch health) is idle. If no runner is online, it waits (up to 24 hours) rather than falling
back to GitHub-hosted. So turn the variable off before taking the servers down.

### Switching it on and off

```sh
# on (landing tier)
gh variable set CONCRETE_SELF_HOSTED --body true -R lambdaclass/concrete
# off (back to GitHub-hosted)
gh variable delete CONCRETE_SELF_HOSTED -R lambdaclass/concrete
# campaign tier, separately (normally left off)
gh variable set CONCRETE_SELF_HOSTED_CAMPAIGN --body true -R lambdaclass/concrete
```

The variable is read when a run starts. Runs already queued keep the routing they started with.

**One repository.** Since the owner's decision of 2026-11-06, pending its record in
`docs/decisions.md`, the runners serve lambdaclass/concrete only; concrete2, where they were
registered until then, is archived once a full landing has run on lambdaclass/concrete. Variables
and repository-level runners belong to one repository: the move
re-registered each runner there (the dotfiles `servers/runners.sh`, `RUNNER_REINSTALL=1`, which
reinstalls the runner into a fresh user), and `CONCRETE_SELF_HOSTED=true` is set on
lambdaclass/concrete. The root has no nightly campaign yet; `CONCRETE_SELF_HOSTED_CAMPAIGN` matters
only when one returns.

## Security rules (public repository)

GitHub's own guidance is that self-hosted runners should not be used with public repositories,
because a pull request can run arbitrary code on them. We use them anyway, under these rules:

**Who can reach the runners at all** (owner decision of 2026-11-06, "A", pending its record in
`docs/decisions.md`). On lambdaclass/concrete every org member
has push: 44 accounts. A push of any branch, or a `workflow_dispatch`, runs the workflow file of that
branch, so any of them can put a job on these runners with no approval; the rules below do not
change that. The owner accepted this exposure, as for stabileo's runners. On concrete2 one account
had push.

1. **No `pull_request` event runs on a self-hosted runner.** The `runs-on` expression enforces this
   for the workflow as written. But a pull request runs the workflow file **from the PR branch**, so
   a fork PR can rewrite `runs-on` to `[self-hosted]` and the guard is gone. The guard prevents
   accidents. It does not stop an attacker. Rules 2 and 3 do.
2. **Require approval for all outside collaborators.** In Settings, Actions, General, "Approval for
   running fork pull request workflows from contributors", choose "Require approval for all outside
   collaborators". Before approving a fork PR's run, read its diff to `.github/workflows/`. A
   changed `runs-on`, a new job, or a new trigger is a reason not to approve.
3. **Ephemeral runners in throwaway VMs or containers are recommended.** `./config.sh ...
   --ephemeral` only makes the runner take one job and then unregister. **It does not erase
   anything:** files, surviving processes, cron entries, a modified `~/.bashrc` or toolchain all
   stay on the machine. Isolation comes from destroying the VM or container after each job and
   starting a fresh one from a clean image, which registers a new ephemeral runner. Automate that
   with actions-runner-controller, or with a supervisor **outside** the job's VM or container that
   calls `gh api -X POST repos/lambdaclass/concrete/actions/runners/registration-token`.
   The supervisor's admin token must never be readable from inside a job. Persistent runners (or
   `--ephemeral` re-registered on the same machine, which is the same thing) are acceptable only
   with rule 2, the cleanup hook below and a dedicated low-privilege user, and with the
   understanding that one job can leave state for the next.
4. **Dedicated, unprivileged users and hosts.** Use one Unix user per runner, with no SSH keys,
   cloud credentials or other repositories' secrets readable, and **no sudo**. Don't run other
   services on the host.
5. The triggers that do reach self-hosted runners are `push` to `main`, `push` to other branches
   (branch health), `workflow_dispatch` and `schedule`. All of them need write access to the
   repository. The nightly report job is a `workflow_run` of CI that runs only for a
   `workflow_dispatch` run on `main` (never for a pull request's run) and checks out the default
   branch, so no pull request's code reaches it.

## Server setup

### Host

- Ubuntu 24.04 x86-64, the same image family as `ubuntu-latest`. The `.lake/build` and `~/.elan`
  caches are keyed by `runner.os`/`runner.arch` and shared with GitHub-hosted runs. Lake re-checks
  its traces, so a mismatched cache rebuilds instead of being trusted. But a different distribution
  makes every self-hosted build cold.
- **One runner per ~4 cores**, with at least 8 GB RAM and 30 GB disk each. The Lean build and the
  heavier gates are memory-bound, and a runner that swaps is slower than a GitHub-hosted one. For
  example, a 16-core, 64 GB server takes 4 runners.

### Packages to preinstall

The workflow installs `clang` (and `valgrind` for the examples job) with `sudo apt-get` on
GitHub-hosted runners. On a self-hosted runner it does so **only when the tool is missing**, and the
runner users have no sudo (see below). So preinstall everything:

```sh
sudo apt-get update
sudo apt-get install -y git curl ca-certificates build-essential clang valgrind \
  python3 python3-pip python3-yaml xxd perl tar zstd ripgrep coreutils gh
# Rust (rustc + cargo), per runner user, like the stable toolchain on GitHub-hosted images:
sudo -iu runner1 sh -c 'curl --proto =https --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal'
```

- `rustc` is used by the LL(1) grammar job. `cargo` builds nanoda for the external-checker job
  whenever `~/.cache/concrete-ext` has no build for the pinned SHA. Ubuntu's `rustc` package does
  not pull in `cargo`, so use rustup (or install both `rustc` and `cargo`), and check it once by
  running the external-checker job with an empty `~/.cache/concrete-ext`. Rustup puts its tools in
  `~/.cargo/bin`, so install it before `./config.sh`, or add that directory to the runner's `.path`.
- `python3-yaml` is used by the workflow, example and qualification gates, `xxd` and `curl` by
  the workload differentials, and `zstd` by `actions/cache`. `gh` (GitHub CLI; Ubuntu 24.04 ships
  it as the `gh` package) is used by the nightly workflow's dispatch and report jobs, which run on
  these runners under `CONCRETE_SELF_HOSTED_CAMPAIGN`.
- **Lean (elan) is not preinstalled.** `leanprover/lean-action` installs elan into `~/.elan` on
  first use, and the toolchain stays there: the runner user's home persists between jobs. The
  `~/.elan` cache step runs on GitHub-hosted runners only. On these runners it re-downloaded a
  2.3 GB archive of toolchains the home already held, 2-4 minutes per job and about a third of all
  runner time in a train (measured 2026-10-23). A toolchain bump is installed once per runner by
  lean-action (and the 4.35 leg by its `elan toolchain install` step). With one user per runner,
  each runner has its own `~/.elan`, so concurrent jobs never race on one toolchain directory.
- **Nix** is needed by exactly one job, `Multi-kernel evidence (Rocq + Isabelle)`, which runs
  `nix develop .#provers`. Install multi-user Nix (daemon) **before** configuring the runner, so
  `/nix/var/nix/profiles/default/bin` is on the PATH the runner records in its `.path` file. Enable
  flakes in `/etc/nix/nix.conf` (`experimental-features = nix-command flakes`).
  `cachix/install-nix-action` sees an existing `nix` and skips its own install, so its
  `extra_nix_config` is **not** applied: the system config must carry the flakes setting. The
  provers closure is several GB; a persistent `/nix/store` makes this job much faster than on
  GitHub-hosted runners.
- **Do not install** `z3`, `cvc5`, `coqc`, `isabelle` or `lli` system-wide. Several gates
  treat those as skip-if-absent, so installing them makes a self-hosted run execute legs that the
  GitHub-hosted reference run skips, and the two runs no longer agree. The provers come from the
  Nix shell in the one job that uses them.
- **No sudo.** On a self-hosted runner, the `Install clang` steps run `sudo apt-get` only when
  the tool is missing. Without sudo, that step fails and names the problem, which is the intended
  result: install the package on the host. Do **not** grant passwordless `sudo apt-get`.
  Unrestricted apt arguments give root (apt hooks, `-o` options, local packages), and that defeats
  the per-runner user boundary.

### Installing a runner

Do this once per runner, each in its own user (`runner1`, `runner2`, ...) and its own directory:

```sh
sudo useradd -m -s /bin/bash runner1
sudo -iu runner1
mkdir actions-runner && cd actions-runner
# Take the current version and checksum from Settings, Actions, Runners, New self-hosted runner.
curl -o actions-runner.tar.gz -L https://github.com/actions/runner/releases/download/v<VERSION>/actions-runner-linux-x64-<VERSION>.tar.gz
tar xzf actions-runner.tar.gz
# The token is shown on that settings page (or: gh api -X POST repos/lambdaclass/concrete/actions/runners/registration-token)
./config.sh --url https://github.com/lambdaclass/concrete --token <TOKEN> \
  --name "$(hostname)-runner1" --labels concrete --unattended   # add --ephemeral (recommended)
exit
cd /home/runner1/actions-runner
sudo ./svc.sh install runner1
sudo ./svc.sh start
```

`self-hosted`, `linux` and `x64` are added automatically, and `--labels concrete` adds the fourth
label the workflow asks for.

### State between jobs (persistent runners)

A GitHub-hosted job starts on a fresh VM. A self-hosted one does not. Here is what the workflow
already handles, and what the host has to handle.

- **Workspace.** `actions/checkout@v4` (default `clean: true`) runs `git clean -ffdx` and
  `git reset --hard` on the existing checkout. That removes `.lake/`, `.mutation-evidence/`,
  leftovers of a cancelled mutation shard and any tracked file a gate mutated, before the cache
  restores `.lake/build`. The proof replay's "no build caches" property holds for the same
  reason.
- **`$RUNNER_TEMP`** is emptied by the runner for every job. The workflow's own temporary files
  live there: the LL(1) checker binaries, the trust-gate log, the thesis-demo reports, the example
  outputs, the checker acceptance evidence and the mutation shard records.
- **`/tmp` is NOT cleaned, and many gates write fixed `/tmp/...` paths.** Two runners on one host
  would overwrite each other's files, and a stale file from an earlier job could be read by a later
  one. Give every runner service a private `/tmp`, and empty it when each job starts:

  ```sh
  # Private /tmp per runner service (systemd unit created by svc.sh)
  sudo systemctl edit "$(cat /home/runner1/actions-runner/.service)"
  #   [Service]
  #   PrivateTmp=true
  sudo systemctl restart "$(cat /home/runner1/actions-runner/.service)"
  ```

  ```sh
  # /home/runner1/job-started.sh  (chmod +x), wired up in the runner's .env file:
  #   ACTIONS_RUNNER_HOOK_JOB_STARTED=/home/runner1/job-started.sh
  #!/bin/sh
  # /tmp is private to this runner service (PrivateTmp), so emptying it touches no other process.
  find /tmp -mindepth 1 -maxdepth 1 -user "$(id -u)" -exec rm -rf {} + 2>/dev/null || true
  ```

  An ephemeral runner in a fresh container or VM needs neither.
- **`$HOME` caches** persist: `~/.elan` (the toolchain, keyed by `lean-toolchain`) and
  `~/.cache/concrete-ext`. In that cache, each tool is built into a directory named by its pinned
  SHA and checked against it, and lean4export, which is rebuilt with this repository's toolchain,
  also has that toolchain in its directory name. So a toolchain bump builds a new exporter instead of
  reusing one that cannot read the new `.olean` files. Both caches are keyed by everything their
  builds depend on, so keeping them between jobs makes runs faster without affecting correctness.
  They live in the user's HOME, so each runner has its own. Old directories are never deleted; prune
  `~/.cache/concrete-ext` now and then.
- **Processes.** The runner kills a job's process tree when the job ends. A gate that leaves a
  daemon behind would survive on a persistent runner. That is one more reason to prefer ephemeral
  runners.

## Build cache (R-0546)

Every job, worktree and agent used to build the compiler from nothing. Two caches now start that
build warm. **Neither one skips it.** `lake build` still runs and re-checks every module's trace,
and the BuildIdentity freshness gate still runs.

### Lean: `.lake/build` seeds

`scripts/dev/seed-lake.sh` copies an existing `.lake/build` into a checkout that has none. It
**refuses** (exit 3, nothing copied) unless the source matches on the **seed key**:

- the platform (`uname -s`/`-m`);
- `lean-toolchain`;
- the sha256 of `lake-manifest.json`;
- the sha256 of the **lean executable itself**.

The executable is in the key because lake's traces record only the Lean version and commit. Elan's
official archive and the devshell's autoPatchelf'd Linux copy would otherwise accept each other's
`.olean` files, and a module kernel-checked by one binary would be credited to the other (R-0208).
For a checkout, the script reads the binary from the checkout's own lake traces. Traces from other
Lean versions are ignored, because lake rebuilds those modules anyway.

Sources and `lakefile.toml` are not in the key. A seed from other sources is the useful case, and
lake mixes each module's sources and options into its trace. A source hash only chooses between
cache entries.

| Where | Seed source | How |
|---|---|---|
| Self-hosted CI runner | `/var/cache/concrete-lake/<key>/{<srchash>,latest}` | workflow step `Seed .lake from the server build cache (self-hosted only)` |
| GitHub-hosted runner | `actions/cache` (`.lake/build`, exact source key) and lean-action's `.lake` cache (previous commit) | unchanged |
| New worktree (laptop or server) | the main checkout's `.lake/build` | `bash scripts/dev/seed-lake.sh` (inside `nix develop`), then `lake build` |

- **Every same-version module must name its executable.** A trace from this Lean version that
  does not name the binary that compiled it refuses the whole seed, because it may be a fetched
  artifact or an unknown log format. The check assumes that the binary at a recorded path has not
  been replaced in place. That holds for Nix store paths, which are immutable, and for elan
  toolchains, which use one directory per release.
- **A consistent snapshot.** Lake takes no lock that the seeder could share. A checkout source must
  therefore be quiet: nothing in it may be written from 10 s before the copy
  (`CONCRETE_SEED_QUIET`) until the copy ends. A `lake build` that is running, or has just
  finished, in the main checkout refuses the seed. Provenance is checked again on the copy itself.
  So is the order of writes: an `.olean` or `.ilean` newer than its trace means the build was
  killed or suspended mid-module, and that refuses the seed too. One risk remains and is accepted:
  checkout files edited by hand with matching timestamps are not detected. CI seeds only from
  published entries.
  Published cache entries need neither check. Each one is moved into place whole, after a completed
  build, and never written again. One seeder runs per checkout at a time (`.lake/seed.lock`).
- **CI checks against `~/.elan`'s lean** (`--elan`). That is the binary lean-action builds with,
  whatever else is on `PATH`.
- **Copies, never hardlinks.** Lake rewrites trace files in place, so a hardlink would write through
  into the seed. macOS uses APFS clones (`cp -c`, instant, no extra space). The server uses a plain
  copy, about 1 s for 600 MB.
- In CI, a seeded job sets `use-github-cache: false` on lean-action. Otherwise lean-action would
  restore an older commit's `.lake` over the seed. An exact-hit of the `.lake/build`
  `actions/cache` step comes first. The seed then refuses to overwrite it, which is the right
  outcome, because the exact hit is the better start.
- `--build [args]` seeds and then always `exec`s `lake build args`. The exit status is the build's.
- `scripts/tests/check_build_cache.sh` gates the key, the refusals, the copy-not-link rule,
  publish/consume, and the workflow wiring.

**The cache producer on concrete-ci-1.** The system user `lakecache` (no login, no sudo, home
`/var/lib/concrete-lake`, its own elan) owns `/var/cache/concrete-lake`. That directory is
world-readable and writable only by `lakecache`. `concrete-lake-refresh.timer` runs every 10
minutes and starts `concrete-lake-refresh.service`, which runs at `Nice=15`, `CPUWeight=20` and
`IOWeight=20`, with `ProtectSystem=strict` and `ProtectHome=true`. The service:

1. fetches `origin/main` into `/var/lib/concrete-lake/main`, a persistent clone, so the build is
   incremental;
2. runs `/usr/local/lib/concrete-lake/seed-lake.sh --publish /var/cache/concrete-lake`, which runs
   `lake build` and publishes only if it succeeds.

The service keeps three entries per key and updates `latest` atomically. The installed copy of
`seed-lake.sh` must be updated by hand when the key format changes. The key starts with
`format=concrete-lake-seed-v1`, so a format change makes the old entries miss instead of match
wrongly.

**Why only `lakecache` writes.** Lake trusts a module's stored trace and `.hash` files. A job that
could write the seed could plant an `.olean` file whose trace still matches its sources, and later
jobs would use it without rebuilding. Runner users (`gha1..6`) and `dev` can only read the cache.
The producer builds only `origin/main`, which takes write access to change.

### Nix: binary cache

All local users share one `/nix/store` through nix-daemon. On this host the store already acts as
the cache, so the useful steps are to realize the devshell closures and to protect them from garbage
collection:

- `/nix/var/nix/gcroots/concrete/devshell-default` (116 paths) and `devshell-provers`
  (11.4 GB, Rocq, Isabelle, cvc5), built from `origin/main`'s `flake.lock`;
- `/nix/var/nix/gcroots/concrete/nix-serve-ng` (the server binary).

`concrete-nix-serve.service` serves that store as a **signed** binary cache. It uses nix-serve-ng
from the repository's pinned nixpkgs.

- **Choice of nix-serve-ng.** It serves the live store directly, with no push step, database or
  second copy, and signs narinfos on the fly. Attic adds a server, a database and an upload step,
  and earns that only with several machines that push.
- **Exposure.** It listens on `127.0.0.1:5050` only. The ufw rules are unchanged (OpenSSH only).
  It runs as `DynamicUser`, and the signing key reaches it through systemd `LoadCredential`.
- **Keys.** The secret key is `/etc/nix/concrete-ci-1-cache.sec` (root, 0600). The public key is
  `concrete-ci-1-cache-1:vbcfJrrGDnfqalZ9Tmf0ZsvWY5+UCM77+uHM5aVoyMA=`.
- **Not a substituter on concrete-ci-1 itself.** A local substituter that serves the same store
  can never supply a missing path. It would only add a failed lookup per miss and a new way to fail.
  `/etc/nix/nix.conf` is therefore unchanged, and cache.nixos.org remains the only substituter. A
  second server on the same LAN would add `http://<lan-ip>:5050` (after a ufw rule for that
  interface only) as `extra-substituters`, plus the public key in `extra-trusted-public-keys`.
- **GitHub-hosted runners** never reach it. They keep cache.nixos.org and `actions/cache`. No port
  is opened.
- **The laptop.** The laptop is aarch64-darwin and the server is x86_64-linux, so the server's store
  has nothing a macOS devshell can use. It helps only a Linux builder or VM on the laptop. If one is
  needed, use a tunnel, never a public port:

  ```sh
  ssh -i ~/.ssh/concrete_ci -N -L 5050:127.0.0.1:5050 ubuntu@62.210.216.169 &
  nix build ... --extra-substituters http://127.0.0.1:5050 \
    --extra-trusted-public-keys 'concrete-ci-1-cache-1:vbcfJrrGDnfqalZ9Tmf0ZsvWY5+UCM77+uHM5aVoyMA='
  ```

  `--extra-substituters` is honored only for a trusted user, or when it is listed in the laptop's
  `trusted-substituters`.

## Where the record lives (R-0547)

Every subcommand appends one row to the train's log:

- the time in UTC;
- the train, stage, base and head;
- the members, as `ref@sha`;
- the run id, result and duration;
- a note.

Results use the promotion pipeline's vocabulary:

- `passed`, `failed` and `skipped`;
- `incomplete` for no verdict;
- `refused` and `conflict` for a refusal by the script.

**Decision: the log is kept local, one file per train, in the git common directory**
(`<git-common-dir>/concrete-landing/log/<train>.tsv`). Train state lives next to it, in
`<train>/train.env`. The reasons:

- **Committing it to the train changes the candidate.** A row appended to the train after CI ran
  would land a SHA that CI never validated. The `land` row cannot exist before the land happens.
- **One shared TSV conflicts.** Every train would append to the same file, which recreates the
  ledger conflicts R-0542 removes. One file per train cannot conflict.
- **The common directory is shared by every worktree.** `report.sh` and `train.sh status` see every
  train of the clone from any of its worktrees; building, checking and landing run only in the full
  clone itself ("Where a train runs").

To publish the record, `report.sh --export docs/project/landing_log/` copies the per-train files
into the tree for a documentation-only commit. Per-train files never conflict on rebase. That
directory is what R-0547's generated median, next to the candidate table, will read.

## Readiness

A branch is **ready** when all of the following hold:

- it is on origin, named `wip/<name>`;
- its head commit is not in main;
- its head carries both notes below, published on origin.

| notes ref | lines | writer |
|---|---|---|
| `refs/notes/concrete-review` | `verdict: clean\|findings\|blocked`, `rounds: N`, `reviewer: codex`, `utc: ...`, `base: <sha>`, `pieces: N` | `scripts/review/review.sh` (`scripts/review/verify.sh` reads it) |
| `refs/notes/concrete-gates` | `gates: pass\|fail`, `selected: N`, `utc: ...` | `scripts/land/ready.sh` |

One `key: value` per line; when a key repeats, the last line wins. `scripts/land/notes.sh` reads and
writes the notes (`get`, `put`, `ready`). `put` builds each write on its own temporary ref on top
of the remote's notes tip, pushes that commit without force, and retries on a race. Concurrent
writers therefore never drop each other's notes, including writers that share one clone or its
worktrees.

**Decision: candidates are `wip/*` branches whose head carries both notes. There is no `ready/*`
prefix.** The reasons:

- **A note is bound to a commit.** A new push starts with no notes, so "ready at the exact head"
  needs no extra rule, and no ready branch can go stale.
- **Agents already push `wip/*`.** The pre-push hook's backup tier keeps those pushes cheap, and
  marking a branch ready is a metadata write, not another branch to keep in step.
- **The ready list is a query**, so nothing has to be cleaned up after a landing.

`wip/land-*` is reserved for the remote leg's temporary refs and is never a candidate.

To mark a branch ready, push it, then run `scripts/land/ready.sh wip/<name>` from a clean
checkout at its head. It runs the review, the impact gates and the remote full set in parallel,
then publishes the gates note: `gates: pass` only when every leg that ran passed. A failed review
leg also publishes `gates: fail`, so an older clean verdict cannot keep the head ready. It exits 0
when the head is ready.

## Pipelining

The review, the impact gates and the remote full set do not depend on each other. `ready.sh` and
`train.sh check` therefore start all three together and wait for all of them. The wall time
becomes the slowest leg instead of the sum. Both scripts record each leg's duration, the wall time
and the sum: `ready.sh` in `<git-common-dir>/concrete-landing/ready.tsv`, and `check` as the
`check-legs` row of the train log.

**Measured on 2026-10-22, on branch `wip/landing-bot`.** Two runs of `ready.sh`, each with its legs
started together:

- **Saving.** The impact gates (69 s) and the review (117 s, from the laptop run) finish inside the

- **What dominates.** The remote full set is about 98% of the cost: 87 minutes on a loaded host.

- **Not counted.** Before pipelining, a human orchestrator usually started the review, the impact
  gates and the remote set by hand in sequence, and each hand-off waited for someone to notice
  the previous result. The scripts remove that wait, and this table does not measure it.

# Self-hosted CI runners

The CI workflow (`.github/workflows/lean_action_ci.yml`) and the branch-health workflow can run
their Ubuntu jobs on our own servers instead of GitHub-hosted `ubuntu-latest`. This page covers what
the switch does, how to set up a server, and the security rules for a **public** repository.

## What the switch does

Every Ubuntu job's `runs-on` is:

```yaml
runs-on: ${{ (github.event_name != 'pull_request' && vars.CONCRETE_SELF_HOSTED == 'true') && fromJSON('["self-hosted","linux","x64","concrete"]') || 'ubuntu-latest' }}
```

- The repository variable `CONCRETE_SELF_HOSTED` routes the **landing tier** (build, test suites,
  trust, proof and evidence jobs, the language-surface jobs, multi-kernel) and branch health.
- `CONCRETE_SELF_HOSTED_CAMPAIGN` routes the **campaign tier** (mutation plan, the 24 mutation
  shards, the aggregate, the fuzz campaign, the proof replay) on its own, and the two light jobs of
  the nightly workflow (`nightly.yml`: the dispatch and the report, which need `gh` and `python3`). Leave it unset
  unless the servers can absorb 24 shards of up to ~85 minutes each. Labels give no priority, so a
  campaign on self-hosted runners would queue landing runs behind it.
  The tiers are listed in [PROMOTION_PIPELINE.md](../legacy/docs/project/PROMOTION_PIPELINE.md#ci-tiers).
- An unset variable, or any value other than `true`, means GitHub-hosted. That is the default.
- **A `pull_request` event never runs on a self-hosted runner**, whatever the variables say. See
  the security section for why this guard alone is not enough.
- `Build + main tests (macOS)` stays on `macos-latest`. The Pages workflow (`book.yml`) stays on
  GitHub-hosted runners.

**Two pools.** CI's jobs ask for the label `concrete`; branch health asks for `concrete-light`, a
separate pool of small runners (two on concrete-ci-2, `LIGHT_RUNNERS` in the dotfiles host file).
Branch health runs on every push to every branch, about 500 runs a day, and on the `concrete` pool
those runs took 20-92 runner-minutes out of each train's window (measured 2026-10-24). Labels give
no priority, so the only way to keep a train from queueing behind them is to not share the pool.
A `concrete-light` runner carries only that label, so CI never lands on it either.

### Runner pools and their limits (P13, owner-approved 2026-11-05)

CI runs on two regular pools: concrete-ci-2's self-hosted runners and GitHub-hosted runners. Neither
is a fallback that weakens a check; each required check runs on a pool that can run it, or is
INCOMPLETE and blocks the landing.

| Pool | Where | Limits (set 2026-11-06) | Runs |
|---|---|---|---|
| `concrete` | concrete-ci-2 (Hetzner AX102: 32 threads, 125 GB RAM) | 6 runners `gha1`..`gha6`, so at most 6 concurrent jobs; each has `MemoryMax=28G` and no swap, and no per-runner CPU cap | the landing tier when `CONCRETE_SELF_HOSTED=true`; never a `pull_request` |
| `concrete-light` | concrete-ci-2 | 2 runners `gha7`, `gha8` (`LIGHT_RUNNERS` in the dotfiles host file), each `CPUQuota=400%` and `MemoryMax=8G` | branch health only |
| GitHub-hosted | `ubuntu-latest`, `macos-latest` | GitHub's per-repository concurrency | every landing-tier job when the variable is off; always: `Oracle (GitHub-hosted fetch + smoke)` and `Build + main tests (macOS)`; every `pull_request` |

Both pools on concrete-ci-2 run inside `concrete-runners.slice`, capped together at `CPUQuota=2400%`
(24 of 32 threads), `MemoryMax=96G`, no swap and `TasksMax=16384` (ISS-0007, applied 2026-11-06).
The runners together can therefore never use more than 24 CPU-equivalents or 96 GB, which leaves
8 CPU-equivalents and about 25 GB of headroom for gate runs, agents and logins in `user.slice`. This is
headroom, not a reservation: those processes share it, and only `system.slice`'s 4 GB `MemoryMin` (sshd,
tailscaled) is reserved. The slice keeps the default CPU weight (100) against
`user.slice`'s 25, so CI still wins under contention. There is no `MemoryHigh`: a job past its
`MemoryMax` is killed inside the slice rather than throttled. The values live in the dotfiles host
file (`servers/hosts/concrete-ci-2.env`, `CONCRETE_RUNNERS_*` and `CONCRETE_*RUNNER_*`), and
`servers/runners.sh` writes them, so a rebuilt host gets the same caps.

Manual heavy work on concrete-ci-2 (train check legs through `land.gatesHost`, `run-at-ref.sh`
runs, oracle rebuilds) follows the machine-wide rule: at most two full suites, mutation campaigns
or other CPU-heavy checks at once (AGENTS.md, ROADMAP R-0543).

**What runs where on the GitHub-hosted pool.** Every landing-tier job's `runs-on` falls back to
`ubuntu-latest`, so the whole landing tier can run there; the only self-hosted-only steps are cache
seeding (`Seed .lake from the server build cache`), whose absence means a cold build, never a
skipped check. The oracle differential gets its oracle on a GitHub-hosted runner from the published
release (`scripts/oracle/fetch.sh`: the lock's artifact sha256, install manifest and binary hash);
`scripts/oracle/ci_check.sh` reports a missing, corrupted or unverifiable artifact as INCOMPLETE
(exit 3), which fails the required job (`scripts/checks/oracle_fetch.sh` holds this). The
oracle rebuild (`oracle.yml`, weekly) runs on either pool.

A job routed to self-hosted waits until a runner with **all four** labels `self-hosted`, `linux`,
`x64` and its pool label (`concrete`, or `concrete-light` for branch health) is idle. If no runner is online, it waits (up to 24 hours) rather than falling
back to GitHub-hosted. So turn the variable off before taking the servers down.

## Security rules (public repository)

GitHub's own guidance is that self-hosted runners should not be used with public repositories,
because a pull request can run arbitrary code on them. We use them anyway, under these rules:

**Who can reach the runners at all** (owner decision of 2026-11-06, "A", pending its record in
`docs/decisions.md`). On lambdaclass/concrete every org member
has push: 44 accounts. A push of any branch, or a `workflow_dispatch`, runs the workflow file of that
branch, so any of them can put a job on these runners with no approval; the rules below do not
change that. The owner accepted this exposure, as for stabileo's runners. On concrete2 one account
had push.

1. **No `pull_request` event runs on a self-hosted runner.** The `runs-on` expression enforces this
   for the workflow as written. But a pull request runs the workflow file **from the PR branch**, so
   a fork PR can rewrite `runs-on` to `[self-hosted]` and the guard is gone. The guard prevents
   accidents. It does not stop an attacker. Rules 2 and 3 do.
2. **Require approval for all outside collaborators.** In Settings, Actions, General, "Approval for
   running fork pull request workflows from contributors", choose "Require approval for all outside
   collaborators". Before approving a fork PR's run, read its diff to `.github/workflows/`. A
   changed `runs-on`, a new job, or a new trigger is a reason not to approve.
3. **Ephemeral runners in throwaway VMs or containers are recommended.** `./config.sh ...
   --ephemeral` only makes the runner take one job and then unregister. **It does not erase
   anything:** files, surviving processes, cron entries, a modified `~/.bashrc` or toolchain all
   stay on the machine. Isolation comes from destroying the VM or container after each job and
   starting a fresh one from a clean image, which registers a new ephemeral runner. Automate that
   with actions-runner-controller, or with a supervisor **outside** the job's VM or container that
   calls `gh api -X POST repos/lambdaclass/concrete/actions/runners/registration-token`.
   The supervisor's admin token must never be readable from inside a job. Persistent runners (or
   `--ephemeral` re-registered on the same machine, which is the same thing) are acceptable only
   with rule 2, the cleanup hook below and a dedicated low-privilege user, and with the
   understanding that one job can leave state for the next.
4. **Dedicated, unprivileged users and hosts.** Use one Unix user per runner, with no SSH keys,
   cloud credentials or other repositories' secrets readable, and **no sudo**. Don't run other
   services on the host.
5. The triggers that do reach self-hosted runners are `push` to `main`, `push` to other branches
   (branch health), `workflow_dispatch` and `schedule`. All of them need write access to the
   repository. The nightly report job is a `workflow_run` of CI that runs only for a
   `workflow_dispatch` run on `main` (never for a pull request's run) and checks out the default
   branch, so no pull request's code reaches it.

## Server setup

### Host

- Ubuntu 24.04 x86-64, the same image family as `ubuntu-latest`. The `.lake/build` and `~/.elan`
  caches are keyed by `runner.os`/`runner.arch` and shared with GitHub-hosted runs. Lake re-checks
  its traces, so a mismatched cache rebuilds instead of being trusted. But a different distribution
  makes every self-hosted build cold.
- **One runner per ~4 cores**, with at least 8 GB RAM and 30 GB disk each. The Lean build and the
  heavier gates are memory-bound, and a runner that swaps is slower than a GitHub-hosted one. For
  example, a 16-core, 64 GB server takes 4 runners.

### Packages to preinstall

The workflow installs `clang` (and `valgrind` for the examples job) with `sudo apt-get` on
GitHub-hosted runners. On a self-hosted runner it does so **only when the tool is missing**, and the
runner users have no sudo (see below). So preinstall everything:

```sh
sudo apt-get update
sudo apt-get install -y git curl ca-certificates build-essential clang valgrind \
  python3 python3-pip python3-yaml xxd perl tar zstd ripgrep coreutils gh
# Rust (rustc + cargo), per runner user, like the stable toolchain on GitHub-hosted images:
sudo -iu runner1 sh -c 'curl --proto =https --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal'
```

- `rustc` is used by the LL(1) grammar job. `cargo` builds nanoda for the external-checker job
  whenever `~/.cache/concrete-ext` has no build for the pinned SHA. Ubuntu's `rustc` package does
  not pull in `cargo`, so use rustup (or install both `rustc` and `cargo`), and check it once by
  running the external-checker job with an empty `~/.cache/concrete-ext`. Rustup puts its tools in
  `~/.cargo/bin`, so install it before `./config.sh`, or add that directory to the runner's `.path`.
- `python3-yaml` is used by the workflow, example and qualification gates, `xxd` and `curl` by
  the workload differentials, and `zstd` by `actions/cache`. `gh` (GitHub CLI; Ubuntu 24.04 ships
  it as the `gh` package) is used by the nightly workflow's dispatch and report jobs, which run on
  these runners under `CONCRETE_SELF_HOSTED_CAMPAIGN`.
- **Lean (elan) is not preinstalled.** `leanprover/lean-action` installs elan into `~/.elan` on
  first use, and the toolchain stays there: the runner user's home persists between jobs. The
  `~/.elan` cache step runs on GitHub-hosted runners only. On these runners it re-downloaded a
  2.3 GB archive of toolchains the home already held, 2-4 minutes per job and about a third of all
  runner time in a train (measured 2026-10-23). A toolchain bump is installed once per runner by
  lean-action (and the 4.35 leg by its `elan toolchain install` step). With one user per runner,
  each runner has its own `~/.elan`, so concurrent jobs never race on one toolchain directory.
- **Nix** is needed by exactly one job, `Multi-kernel evidence (Rocq + Isabelle)`, which runs
  `nix develop .#provers`. Install multi-user Nix (daemon) **before** configuring the runner, so
  `/nix/var/nix/profiles/default/bin` is on the PATH the runner records in its `.path` file. Enable
  flakes in `/etc/nix/nix.conf` (`experimental-features = nix-command flakes`).
  `cachix/install-nix-action` sees an existing `nix` and skips its own install, so its
  `extra_nix_config` is **not** applied: the system config must carry the flakes setting. The
  provers closure is several GB; a persistent `/nix/store` makes this job much faster than on
  GitHub-hosted runners.
- **Do not install** `z3`, `cvc5`, `coqc`, `isabelle` or `lli` system-wide. Several gates
  treat those as skip-if-absent, so installing them makes a self-hosted run execute legs that the
  GitHub-hosted reference run skips, and the two runs no longer agree. The provers come from the
  Nix shell in the one job that uses them.
- **No sudo.** On a self-hosted runner, the `Install clang` steps run `sudo apt-get` only when
  the tool is missing. Without sudo, that step fails and names the problem, which is the intended
  result: install the package on the host. Do **not** grant passwordless `sudo apt-get`.
  Unrestricted apt arguments give root (apt hooks, `-o` options, local packages), and that defeats
  the per-runner user boundary.

### State between jobs (persistent runners)

A GitHub-hosted job starts on a fresh VM. A self-hosted one does not. Here is what the workflow
already handles, and what the host has to handle.

- **Workspace.** `actions/checkout@v4` (default `clean: true`) runs `git clean -ffdx` and
  `git reset --hard` on the existing checkout. That removes `.lake/`, `.mutation-evidence/`,
  leftovers of a cancelled mutation shard and any tracked file a gate mutated, before the cache
  restores `.lake/build`. The proof replay's "no build caches" property holds for the same
  reason.
- **`$RUNNER_TEMP`** is emptied by the runner for every job. The workflow's own temporary files
  live there: the LL(1) checker binaries, the trust-gate log, the thesis-demo reports, the example
  outputs, the checker acceptance evidence and the mutation shard records.
- **`/tmp` is NOT cleaned, and many gates write fixed `/tmp/...` paths.** Two runners on one host
  would overwrite each other's files, and a stale file from an earlier job could be read by a later
  one. Give every runner service a private `/tmp`, and empty it when each job starts:

  ```sh
  # Private /tmp per runner service (systemd unit created by svc.sh)
  sudo systemctl edit "$(cat /home/runner1/actions-runner/.service)"
  #   [Service]
  #   PrivateTmp=true
  sudo systemctl restart "$(cat /home/runner1/actions-runner/.service)"
  ```

  ```sh
  # /home/runner1/job-started.sh  (chmod +x), wired up in the runner's .env file:
  #   ACTIONS_RUNNER_HOOK_JOB_STARTED=/home/runner1/job-started.sh
  #!/bin/sh
  # /tmp is private to this runner service (PrivateTmp), so emptying it touches no other process.
  find /tmp -mindepth 1 -maxdepth 1 -user "$(id -u)" -exec rm -rf {} + 2>/dev/null || true
  ```

  An ephemeral runner in a fresh container or VM needs neither.
- **`$HOME` caches** persist: `~/.elan` (the toolchain, keyed by `lean-toolchain`) and
  `~/.cache/concrete-ext`. In that cache, each tool is built into a directory named by its pinned
  SHA and checked against it, and lean4export, which is rebuilt with this repository's toolchain,
  also has that toolchain in its directory name. So a toolchain bump builds a new exporter instead of
  reusing one that cannot read the new `.olean` files. Both caches are keyed by everything their
  builds depend on, so keeping them between jobs makes runs faster without affecting correctness.
  They live in the user's HOME, so each runner has its own. Old directories are never deleted; prune
  `~/.cache/concrete-ext` now and then.
- **Processes.** The runner kills a job's process tree when the job ends. A gate that leaves a
  daemon behind would survive on a persistent runner. That is one more reason to prefer ephemeral
  runners.

1. Settings, Actions, Runners lists each runner as Idle, with labels
   `self-hosted, Linux, X64, concrete`.
2. `gh variable set CONCRETE_SELF_HOSTED --body true -R lambdaclass/concrete`.
3. `gh workflow run CI --ref main -R lambdaclass/concrete` (landing tier only), then

## Build cache (R-0546)

Every job, worktree and agent used to build the compiler from nothing. Two caches now start that
build warm. **Neither one skips it.** `lake build` still runs and re-checks every module's trace,
and the BuildIdentity freshness gate still runs.

### Lean: `.lake/build` seeds

`scripts/dev/seed-lake.sh` copies an existing `.lake/build` into a checkout that has none. It
**refuses** (exit 3, nothing copied) unless the source matches on the **seed key**:

- the platform (`uname -s`/`-m`);
- `lean-toolchain`;
- the sha256 of `lake-manifest.json`;
- the sha256 of the **lean executable itself**.

The executable is in the key because lake's traces record only the Lean version and commit. Elan's
official archive and the devshell's autoPatchelf'd Linux copy would otherwise accept each other's
`.olean` files, and a module kernel-checked by one binary would be credited to the other (R-0208).
For a checkout, the script reads the binary from the checkout's own lake traces. Traces from other
Lean versions are ignored, because lake rebuilds those modules anyway.

Sources and `lakefile.toml` are not in the key. A seed from other sources is the useful case, and
lake mixes each module's sources and options into its trace. A source hash only chooses between
cache entries.

| Where | Seed source | How |
|---|---|---|
| Self-hosted CI runner | `/var/cache/concrete-lake/<key>/{<srchash>,latest}` | workflow step `Seed .lake from the server build cache (self-hosted only)` |
| GitHub-hosted runner | `actions/cache` (`.lake/build`, exact source key) and lean-action's `.lake` cache (previous commit) | unchanged |
| New worktree (laptop or server) | the main checkout's `.lake/build` | `bash scripts/dev/seed-lake.sh` (inside `nix develop`), then `lake build` |

- **Every same-version module must name its executable.** A trace from this Lean version that
  does not name the binary that compiled it refuses the whole seed, because it may be a fetched
  artifact or an unknown log format. The check assumes that the binary at a recorded path has not
  been replaced in place. That holds for Nix store paths, which are immutable, and for elan
  toolchains, which use one directory per release.
- **A consistent snapshot.** Lake takes no lock that the seeder could share. A checkout source must
  therefore be quiet: nothing in it may be written from 10 s before the copy
  (`CONCRETE_SEED_QUIET`) until the copy ends. A `lake build` that is running, or has just
  finished, in the main checkout refuses the seed. Provenance is checked again on the copy itself.
  So is the order of writes: an `.olean` or `.ilean` newer than its trace means the build was
  killed or suspended mid-module, and that refuses the seed too. One risk remains and is accepted:
  checkout files edited by hand with matching timestamps are not detected. CI seeds only from
  published entries.
  Published cache entries need neither check. Each one is moved into place whole, after a completed
  build, and never written again. One seeder runs per checkout at a time (`.lake/seed.lock`).
- **CI checks against `~/.elan`'s lean** (`--elan`). That is the binary lean-action builds with,
  whatever else is on `PATH`.
- **Copies, never hardlinks.** Lake rewrites trace files in place, so a hardlink would write through
  into the seed. macOS uses APFS clones (`cp -c`, instant, no extra space). The server uses a plain
  copy, about 1 s for 600 MB.
- In CI, a seeded job sets `use-github-cache: false` on lean-action. Otherwise lean-action would
  restore an older commit's `.lake` over the seed. An exact-hit of the `.lake/build`
  `actions/cache` step comes first. The seed then refuses to overwrite it, which is the right
  outcome, because the exact hit is the better start.
- `--build [args]` seeds and then always `exec`s `lake build args`. The exit status is the build's.
- `scripts/tests/check_build_cache.sh` gates the key, the refusals, the copy-not-link rule,
  publish/consume, and the workflow wiring.

**The cache producer on concrete-ci-1.** The system user `lakecache` (no login, no sudo, home
`/var/lib/concrete-lake`, its own elan) owns `/var/cache/concrete-lake`. That directory is
world-readable and writable only by `lakecache`. `concrete-lake-refresh.timer` runs every 10
minutes and starts `concrete-lake-refresh.service`, which runs at `Nice=15`, `CPUWeight=20` and
`IOWeight=20`, with `ProtectSystem=strict` and `ProtectHome=true`. The service:

1. fetches `origin/main` into `/var/lib/concrete-lake/main`, a persistent clone, so the build is
   incremental;
2. runs `/usr/local/lib/concrete-lake/seed-lake.sh --publish /var/cache/concrete-lake`, which runs
   `lake build` and publishes only if it succeeds.

The service keeps three entries per key and updates `latest` atomically. The installed copy of
`seed-lake.sh` must be updated by hand when the key format changes. The key starts with
`format=concrete-lake-seed-v1`, so a format change makes the old entries miss instead of match
wrongly.

**Why only `lakecache` writes.** Lake trusts a module's stored trace and `.hash` files. A job that
could write the seed could plant an `.olean` file whose trace still matches its sources, and later
jobs would use it without rebuilding. Runner users (`gha1..6`) and `dev` can only read the cache.
The producer builds only `origin/main`, which takes write access to change.

### Nix: binary cache

All local users share one `/nix/store` through nix-daemon. On this host the store already acts as
the cache, so the useful steps are to realize the devshell closures and to protect them from garbage
collection:

- `/nix/var/nix/gcroots/concrete/devshell-default` (116 paths) and `devshell-provers`
  (11.4 GB, Rocq, Isabelle, cvc5), built from `origin/main`'s `flake.lock`;
- `/nix/var/nix/gcroots/concrete/nix-serve-ng` (the server binary).

`concrete-nix-serve.service` serves that store as a **signed** binary cache. It uses nix-serve-ng
from the repository's pinned nixpkgs.

- **Choice of nix-serve-ng.** It serves the live store directly, with no push step, database or
  second copy, and signs narinfos on the fly. Attic adds a server, a database and an upload step,
  and earns that only with several machines that push.
- **Exposure.** It listens on `127.0.0.1:5050` only. The ufw rules are unchanged (OpenSSH only).
  It runs as `DynamicUser`, and the signing key reaches it through systemd `LoadCredential`.
- **Keys.** The secret key is `/etc/nix/concrete-ci-1-cache.sec` (root, 0600). The public key is
  `concrete-ci-1-cache-1:vbcfJrrGDnfqalZ9Tmf0ZsvWY5+UCM77+uHM5aVoyMA=`.
- **Not a substituter on concrete-ci-1 itself.** A local substituter that serves the same store
  can never supply a missing path. It would only add a failed lookup per miss and a new way to fail.
  `/etc/nix/nix.conf` is therefore unchanged, and cache.nixos.org remains the only substituter. A
  second server on the same LAN would add `http://<lan-ip>:5050` (after a ufw rule for that
  interface only) as `extra-substituters`, plus the public key in `extra-trusted-public-keys`.
- **GitHub-hosted runners** never reach it. They keep cache.nixos.org and `actions/cache`. No port
  is opened.
- **The laptop.** The laptop is aarch64-darwin and the server is x86_64-linux, so the server's store
  has nothing a macOS devshell can use. It helps only a Linux builder or VM on the laptop. If one is
  needed, use a tunnel, never a public port:

  ```sh
  ssh -i ~/.ssh/concrete_ci -N -L 5050:127.0.0.1:5050 ubuntu@62.210.216.169 &
  nix build ... --extra-substituters http://127.0.0.1:5050 \
    --extra-trusted-public-keys 'concrete-ci-1-cache-1:vbcfJrrGDnfqalZ9Tmf0ZsvWY5+UCM77+uHM5aVoyMA='
  ```

  `--extra-substituters` is honored only for a trusted user, or when it is listed in the laptop's
  `trusted-substituters`.
