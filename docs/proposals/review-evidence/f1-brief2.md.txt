- **Location:** [scripts/checks/lib/stack_bound.py:42-45](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/scripts/checks/lib/stack_bound.py#L42-L45), [scripts/checks/lib/stack_bound.py:229-241](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/scripts/checks/lib/stack_bound.py#L229-L241), [Concrete/README.md:586](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/Concrete/README.md#L586)
- **Problem:** The stated premise is that *every stack byte lies farther than `TP_REACH` bytes from each thread-pointer base, in either direction* (i.e. $|s - \text{base}| \ge \text{TP\_REACH} + 1 = 257$). However, [`x86_inst`](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/scripts/checks/lib/stack_bound.py#L233-L241) only checks `abs(k) > TP_REACH` on the starting displacement `k` and `continue`s before parsing the operand's `X86_SIZE` width (lines 248-250). A multi-byte access such as `mov qword ptr fs:[0x100], rax` has `k = 0x100 <= TP_REACH` (accepted with `bound 0`), but touches bytes `fs_base + 0x100 .. fs_base + 0x107` (distances `256 .. 263`), so bytes `fs_base + 257 .. fs_base + 263` can lie on the stack while the stated premise holds. (The same applies to `rip`-relative operands, where `rip` is `next_pc = addr + insn_len` and the access spans `size` bytes, and to `fs:[]` with empty brackets where `terms = []` gives `k = 0`.)
- **Long-term fix:** Require non-empty `terms`, parse the operand size `sz = X86_SIZE[size.group(1)]` for all memory operands (not only stack-based ones), and require the entire accessed byte range `[k, k + sz - 1]` to lie within the reach bound (`-TP_REACH <= k` and `k + sz - 1 <= TP_REACH`).

#### 5. Medium — Long-term model of `TP_REACH`, `gs:` on `x86_64-linux`, and `PT_TLS`
- **Location:** [scripts/checks/lib/stack_bound.py:42-46](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/scripts/checks/lib/stack_bound.py#L42-L46), [scripts/checks/lib/stack_bound.py:203-205](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/scripts/checks/lib/stack_bound.py#L203-L205), [Concrete/README.md:586](file:///tmp/claude-30035/-home-unbalancedparen-projects-concrete2/e2c54e65-31b5-4145-8101-c2d7b071b97e/scratchpad/rev-f1b/src/Concrete/README.md#L586)
- **Problem:**
  1. **`gs:` is not a thread-pointer base on `x86_64-linux`:** The only x86 target in `TARGETS` is `x86_64-linux`. Under the System V x86-64 Linux ABI, `%fs` is the thread pointer (`FS.base` points to the TCB), whereas `%gs` is unused in user space and has `GS.base = 0x0` (the null page). Describing `gs` as a "thread-pointer base" on `x86_64-linux` and exempting `gs:[-0x100 .. 0x100]` is inaccurate and unnecessary; `gs:` should be refused outright on `x86_64-linux`.
  2. **Arbitrary `TP_REACH = 0x100` vs. binary TLS metadata and ABI TCB layout:** Under x86-64 ELF Variant II TLS, static TLS variables (`.tdata`/`.tbss`) lie at *negative* offsets `[FS.base - tls_memsz, FS.base)` whose bound is given by the binary's `PT_TLS` program header (`p_memsz`), while the ABI TCB header (`tcbhead_t`, including the stack canary at `fs:0x28`) lies at small *non-negative* offsets `[FS.base, FS.base + TCB_SIZE)`. In slice 0, binaries have no `PT_TLS` header (so negative `fs:` offsets have no reason to be accepted at all), and once TLS exists (or if linked libc/runtime uses `PT_TLS`), a magic `0x100` is both too permissive when `PT_TLS` is absent and too small when `PT_TLS` exceeds 256 bytes.
- **Long-term fix:** Refuse `gs:` on `x86_64-linux`. For `fs:` on `x86_64-linux`, bound negative offsets `[ -tls_size, 0 )` by the binary's `PT_TLS` `p_memsz` (0 when the binary has no `PT_TLS` segment) and bound non-negative offsets `[ 0, TCB_REACH )` (or specifically the TCB fields / `0 .. 0x70`) above `FS.base`, so the premise is tied to the actual ELF TLS/TCB layout rather than a symmetric magic constant around both `fs` and `gs`.

5. **Any regression to existing bounds?**
   - None on the 64 slice-0 disassemblies (none contain `fs:` or `gs:` operands).
