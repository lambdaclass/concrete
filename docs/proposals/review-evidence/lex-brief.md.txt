ONLY THESE RULES ARE SETTLED; build nothing else:
1. The source is a byte string that must be well-formed UTF-8 (the Unicode Standard, Table 3-7:
   no overlong forms, no surrogates U+D800..U+DFFF, nothing above U+10FFFF, no truncated sequence).
2. NUL (U+0000) anywhere in the source is refused.
3. A byte-order mark (U+FEFF) is refused (anywhere, including at the start).
4. A shebang line is not supported: no special treatment of a leading `#!` (it is whatever the
   token rules make of it later, so do not lex it; just do not add any shebang rule).
5. Line comments: `//` up to, not including, the next LF (0x0A) or CR (0x0D), or to end of input.
   There are NO block comments: `/*` is not a comment opener (do not give it any meaning here).
6. Identifier characters are ASCII only: a start character is `A`-`Z`, `a`-`z` or `_`; a continue
   character is a start character or `0`-`9`. Non-ASCII characters are never identifier characters.
NOT SETTLED (do not define): the token set, keywords, punctuation, literals, whitespace other than
what the comment rule needs, the Token type, error-message wording, CLI spellings. Exact spellings
of anything user-visible go through an owner round later.
