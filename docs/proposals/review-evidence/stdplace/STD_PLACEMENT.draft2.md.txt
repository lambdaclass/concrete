## 1. Placement rules used

These rules restate decided principles; each placement below follows from them.

- **P0. There are no std modules before slice 17.** Modules, `pub`, imports and paths arrive at
  17. Before 17, library code a stage needs is written inside the consuming program, in the
  program's own file, and calls primitives by the names the closed builtin table gives them
  (item 32). At 17 that code moves, unchanged in meaning and with its theorems, into the std module
  this table names, and consumers switch to qualified use (`bytes::read_u32_be(...)`, item 11(b)).
  It moves; it is not copied, so each fact keeps one definition (rule 5). Where a row below says a
  module "arrives" before 17, it means its code first exists at that slice inside its consumer, and
  its std module exists from 17. How primitives are named before and after 17 is owner question O6.
- **P1. Code arrives at its first adopted consumer's slice,** not at the slice whose language could
  first express it. A consumer is an adopted showcase stage (the seven showcases and their slices
  are adopted; the per-slice examples in `EXAMPLES.md` are still a proposal) or another std module
  that has one. Consumers that exist only in the proposed examples are marked *(proposed example)*
  and do not by themselves place a module.
- **P2. What goes in std.** A std module is a substrate with a contract independent of its
  consumer (an external standard such as RFC 8439, the Yellow Paper's arithmetic or CRC-32, or a
  target service from the grant table), consumed by at least one adopted stage. A showcase's own
  subject, the thing its row names (the regex engine of grep, DEFLATE and the QOI codec of the
  image decoder, the EVM and Wasm interpreters, the KV store's log), stays in the showcase until a
  second consumer appears. So the theorem about a substrate is stated once, and the showcase's
  theorems are about the showcase.
- **P3. The slice-local API uses only that slice's language** (with P0 for modules). No API at
  slice N names a construct from a later slice; later surface is a later addition to the same code.
- **P4. Second-class references shape every API.** No std function returns a view or stores one.
  Functions take views as downward parameters and return owned values, `Copy` coordinates
  (offsets, lengths, positions) or `Result`s; callers form subviews with the one decided borrow
  form. This is the legacy `ByteCursor` idea (R-0483, "a cursor stores coordinates only",
  `legacy/std/src/numeric.con`), carried as a design, not as code.
- **P5. No hidden traps in std.** Every operation that can fail returns a typed `Result` or takes
  evidence through `#[requires]`. Every loop carries termination evidence; where it rests on an
  environment response (a blocking read or write), the evidence bounds the completed iterations
  and names the response premise, and never claims that a blocking request completes (C6).
- **P6. One form per situation.** One owned growable byte container (`vec::Vec<u8, A>`), not a
  second `Bytes` type; one module per grant family; no std wrapper that restates a language form
  (`assert`, `#[test]`, `match` on `Option`/`Result`).
- **P7. Primitive versus std code.** An operation beneath the safe language (argv, file
  descriptors, sockets, entropy) is a registered primitive with a complete C9 contract. Everything
  expressible in the safe language at its slice is ordinary Concrete with program theorems. Raw
  pointers arrive at 24, so no std code before 24 touches raw memory.
- **P8. Authority is explicit.** Every allocating operation takes the allocator value and
  `with(Alloc)` (authority rule 2: a resource value plus a permission); a container's stored
  release context is not authority to allocate. Every grant operation follows the decided grant
  table, including its narrowing and ending operations.
- **P9. Spellings are illustrative.** Sketches use the decided shapes (`Type::f(x)`, qualified use
  after 17, written local types, `-> Unit`, no `as`, no `char`, no `print`). View parameter types are
  written `&[u8]` / `&mut [u8]` as a placeholder for the open view-type spelling (owner question O1);
  exact names come in the spelling round.

## 2. Placement table

Columns: code arrives (slice, with P0); the slice-local API (illustrative); spec home in C1–C10;
laws and proofs due; the adopted stage that consumes it; the design risk it tests.

Design risks: **R-ref** second-class references at scale; **R-lin** linear ownership in
containers; **R-trap** proof cost of no hidden traps; **R-err** explicit error propagation (no
`?`); **R-cb** callbacks with contracts; **R-grant** grants and `with(...)`; **R-ct** constant time
and secrets.

## 3. The six flagged gaps

### Gap 1: arguments for `grep PATTERN FILE` at 18, without allocation

**Recommendation: one `env` module for the one `Environment` grant, giving each argument as a
scoped view of the immutable launch snapshot, with no allocation and no copy.** This is the
contract the approved grant table already states ("args and allowlisted vars, read with
`with(Env)`; scoped views, no allocation", Q7.10; "scoped immutable launch environment snapshot",
Q7.5), so the recommendation follows a decided row instead of inventing one. The argument is bytes;
grep validates it with `text::validate_utf8` if it needs text. No `cli` is needed at 18. The legacy
`args::get` (an allocating `String`, `""` on invalid UTF-8, which hides a failure) is not carried.
The language part is owner question O2: how the one borrow form takes a grant-owned argument as its
source.

**Runner-up: `env::arg_into(e: &Environment, i: u64, out: &mut [u8]) with(Env) ->
Result<u64, ArgError>`**, copying into a caller buffer, with `ArgError::TooLong` and
`ArgError::NoSuchArgument`. It needs no new borrow source and is equally zero-heap, but it copies,
forces a maximum length on the program, and departs from the decided "scoped views" wording, so it
would need a recorded revision of that row.

Flagged for the owner (not a language question): under the decided filesystem rules FILE is a path
inside a granted `Directory` (`--dir NAME=PATH:RIGHTS`); an absolute path or `..` is refused. The
showcase's command line is `grep PATTERN FILE` with FILE relative to the granted directory, and its
claim wording should say so.

### Gap 2: a non-allocating byte substrate before `Vec` at 22

**Recommendation: `bytes` code arrives at 15 (a std module from 17) as free functions over borrowed
public `u8` views plus `Copy` coordinate structs, and never owns storage.** Storage is always a
language form or a container: a fixed array `[u8; N]` (15), a `HeapArray<u8, A>` (21) or a
`vec::Vec<u8, A>` (22). The same functions serve all three, because each lends the same view type
(owner question O1). The owned growable byte buffer is `vec::Vec<u8, A>`; there is no separate
`Bytes` type (P6). Secret bytes are not handled by `bytes`: the crypto modules carry their own
secret-preserving word loads and stores, because a public codec cannot read `Secret<u8>` and equal
layout authorizes no release (O9 asks whether one generic codec could serve both). The legacy
`Bytes` (raw pointer, length, capacity, allocating `slice`) is not carried; its coordinate cursor
and views (R-0483) are carried as a design.

**Runner-up: an owned `bytes::Bytes<A>` type at 21 over `HeapArray<u8, A>`, plus the view functions.**
It names a byte owner, but at 22 it is a second owned byte container beside `Vec<u8, A>`, which rule 2
refuses, and it adds nothing a view function cannot do.

### Gap 3: EVM growable memory at 21 versus a fixed `HeapArray`

**Recommendation: EVM memory at 21 grows by replacement inside the showcase: a `HeapArray<u8, A>`
holding the current capacity; an expansion beyond it allocates a larger `HeapArray` (capacity at
least doubling, so total copying stays linear), copies the logical prefix, zero-fills the extension
and releases the old array.** No `Vec` is needed, resident memory follows the memory the program
actually touches, and peak bytes are bounded by old plus new capacity. Expansion charges the gas
difference `C_mem(new) − C_mem(old)`, with `C_mem(a) = 3a + ⌊a²/512⌋` for `a` words (execution
specs). Two different outcomes stay distinct: the EVM's out-of-gas halt (part of the modelled EVM
behaviour) and host allocation failure (a typed `AllocFailure` reported as a host resource result,
never as an EVM outcome). The equivalence with the EVM specification is claimed for runs whose
allocations succeed. The resource claim becomes: logical memory ≤ the largest size the gas limit
can pay for (for 30,000,000 gas, 123,169 words = 3,941,408 bytes, about 3.76 MiB), and heap bytes
≤ twice that, plus a configured cap if the program sets one. Wasm 21 uses the same structure for
linear memory: a module's maximum is optional (absent, the Wasm32 limit is 65,536 pages = 4 GiB), so
a configured cap is required, and `memory.grow` past it, or on allocation failure, returns −1, which
the Wasm specification allows.

**Runner-up: preallocate once the size `min(gas bound, configured cap)`, zero-filled, with `msize`
tracked inside it.** Simpler code and no copying, but it charges every transaction the maximum
memory and the zero-filling work even when it touches none, and it can fail allocation for a run
that would have succeeded with growth.

### Gap 4: endian codecs, CRC32, Keccak and hash

**Recommendation:**
- **Public endian codecs in `bytes`** (code at 15, first consumer EVM 15), with the byte order in
  the function name, never the target's native order. Secret word loads and stores live in the
  crypto modules (gap 2).
- **CRC32 in `checksum` at 21**, first consumer PNG. Adler-32 stays inside the PNG showcase's zlib
  code (P2: DEFLATE is the showcase's subject).
- **Keccak in `keccak` at 21**, in the EVM stage that adds memory, where KECCAK256 (which hashes a
  memory range) is implemented; the 23 stage completes gas. It implements Ethereum's original
  Keccak padding and is distinguished from FIPS 202 SHA3-256 by name and theorem.
- **`hash` only with `HashMap`**, when the KV store's measurements pull it (item 19), as a `Hash`
  trait plus one specified keyed function chosen then. `OrderedMap` needs only `Ord`.
- **SHA-256 / BLAKE2s and HKDF** with the tunnel after 28.

**Runner-up:** a separate `endian` module and one `digest` module holding CRC32, Keccak and later
SHA-256. Rejected as primary because CRC32 is an integrity code, not a digest, and grouping
"hash-like" functions mixes public and secret-relevant contracts under one module.

### Gap 5: wide-integer arithmetic for EVM 15 and X25519/Poly1305

**Recommendation: no new integer type.** `u256::U256` at 15 is a `Copy` struct of four `u64` limbs
(32 bytes) whose multiplication uses 32-bit half products, so every intermediate fits `u64`; the
field arithmetic stays inside `poly1305` (26-bit limbs) and `x25519` (25.5-bit limbs), where every
product of two limbs fits `u64`. This needs only slice-2 integers, slice-9 structs and slice-15
arrays. Its cost is the limb-carry proofs, which are exactly the proof cost the no-hidden-traps rule
asks std to pay, and the crypto versions use only the closed constant-time operations on
`Secret<u64>` (O7). The field code is specialized and constant time; it is not a general bignum.

**Runner-up: a `u128` type, or one widening-multiply primitive returning a `Copy` struct of two
halves, added when measurements show the half-product code is too slow** (rule 17). That is a
language addition (owner question O5).

### Gap 6: base64 at 17

**Recommendation: no std `base64`.** No adopted stage consumes it; the slice-17 base64 program is a
proposed example. If that example is adopted, base64 lives in the example's own modules (whose
purpose is to exercise modules), with a caller-buffer API that needs no allocation:
`encoded_len(n: u64) -> Result<u64, Overflow>`, `encode(input: &[u8], out: &mut [u8]) ->
Result<u64, Base64Error>`, `decode(input: &[u8], out: &mut [u8]) -> Result<u64, Base64Error>`, with
typed errors for short output, invalid byte, bad padding and non-canonical trailing bits. It moves
to std when an adopted consumer appears.

**Runner-up: std `base64` at 17 with the same API.** It costs a std module, its laws and its
spelling-round surface with no adopted consumer.

## 4. Std item versus language form

**Language, or stays language (no std module):**
- fixed arrays, views, `swap_at`, array `Destroy` (15): language (OD35); legacy `slice.con` dropped.
- UTF-8 text views (16) and `StaticStr`: language, as the slice table says.
- `Option` and `Result` (12): builtin; no helper module until a consumer needs combinators.
- `test`: `#[test]` and `assert` are the one form; the legacy helper module is dropped.
- `Allocator`, arenas, `Heap` (19), `HeapArray` (21): language types with C9 contracts.
- Grant operations (console, fs, env, net, time, entropy): primitives with C9 contracts.

**Std code, not language:**
- `String<A>`: std code over `vec::Vec<u8, A>` with a struct invariant.
- `OrderedMap`, `HashMap`: std code with no privilege (item 19); Q2.3's destruction order stays a
  binding contract that the std implementation proves.
- Validation and decoding operations on text (16): std `text` code, provable as program theorems.
- `ct_eq` on arrays and views (15): could be std code over the scalar constant-time table (a loop
  whose trip count is the public length), shrinking the trusted primitive table (O6).

**Open (owner question O3):** `Vec<T, A>` (22). Its spare capacity is uninitialized. Safe Concrete
before 24 can express that only by paying a tag per slot (`HeapArray<Option<T>>`, which with
today's `i32` enum tags, foundation question 4, is eight times the storage of `Vec<u8>`), so `Vec`
needs either (a) to be a language container like `HeapArray`, using C4's per-slot initialization,
or (b) std code over one new primitive, a capacity buffer with explicit per-slot initialized
state. Recommended: (a), because it adds one container rather than a general uninitialized-memory
primitive to the safe language.

## 6. Owner questions (language; not decided here)

- **O1. The view type as a parameter.** Every byte module needs one view type, of any length, that
  fixed arrays (15), `HeapArray` (21) and `Vec` (22) all lend, without const generics. Is the
  slice-15 range view such a type, usable as a function parameter, and how is it spelled?
  (Spelling round, item 59, OPEN-21.)
- **O2. Views of grant-owned storage.** How does the one borrow form take an `Environment` argument
  (and a variable) as its source, as the grant table's "scoped views" require? Can the launch
  snapshot be a borrow root?
- **O3. `Vec`'s representation:** a language container (recommended) or std code over a new
  capacity-buffer primitive (section 4).
- **O4. Reading container elements without returned references.** How does a caller read a
  non-`Copy` value in a map or vector: a scoped borrow of an element (a language form over a
  container place) or a function-value callback (20)? This shapes every container API.
- **O5. Wide arithmetic.** Keep 64-bit integers and limb code (recommended now), or add `u128` or a
  widening-multiply primitive when measurements show the need?
- **O6. Primitive or std, and where primitives are named.** Are `ct_eq` on views and UTF-8
  validation primitives or std code (recommended: std code)? How is a validated text view formed
  from a byte view? Are primitives bare names in the closed builtin table (item 32), and do they
  stay bare after 17 or move to std module paths used qualified (item 11(b))?
- **O7. Constant-time table contents.** Does slice 7's closed table include 64-bit multiplication
  (variable time on some targets, so a named backend premise), which Poly1305 and X25519 need, and
  rotation by a public constant, which ChaCha20 needs?
- **O8. Constant arrays.** Are compile-time constants of array type (the CRC32 table, Keccak round
  constants) in the closed initializer subset (item 26, Q6.4)?
- **O9. One implementation for public and secret data.** Can one function be generic over public
  and `Secret<T>` element types (a byte codec, Keccak or SHA-256 used on both), or does each need
  two versions?
- **O10. Several results from one function.** A quarter round returns four words and a wide product
  two halves. With no tuples in the slice table, the one form is a `Copy` struct (from 9). Is that
  intended, so the slice-7 crypto stage is the ARX steps only?
- **O11. Trait laws.** `Ord` (and later `Hash`) needs laws that every impl must prove (a total
  order; hash consistent with equality). How does a trait state an obligation its impls discharge?
- **O12. The entropy draw at slice 7.** Before references (13) and structs (9), how does a draw
  use the grant: by value with the grant returned, by a special primitive form, or another shape?
  This belongs with the slice-6 grant shape (foundation question 14).

Not language questions, flagged for the owner: grep's FILE is relative to a granted directory
(gap 1); the file encryptor's nonce scheme and the randomness/nonce audit (section 5); QOI's 19
stage needs a fixed maximum image size until `HeapArray` (section 5).
