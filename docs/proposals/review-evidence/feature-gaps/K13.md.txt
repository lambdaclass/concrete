# K13. Diagnostics at Elm quality (owner, 2026-11-08, verbatim: "i want to have elm like errors for item 1 so we need to make sure they are good"; item 1 = K1 source provenance)

Claude's proposal, to be judged against Elm, rustc, Gleam and Roc:
a. Diagnostics as structured data with one renderer: each diagnostic carries a title, the rule ID (Lean rule name + revision), a primary span, labelled secondary spans ("moved here", "used again here"), a plain-language explanation and an optional fix hint. The same record renders as Elm-style terminal text and as JSON lines for agents (decided diagnostics row; K12; R-0593).
b. What provenance (K1) must carry: spans with both ends (byte offsets plus line/column; decided: byte columns, a tab counts one byte), related spans across passes (a refusal found after elaboration or Mono still points at written source), and type-origin tracking ("this is u8 because of here"). K1's design must supply all of it.
c. One explanation page per rule ID, with a failing example and its fixed version, generated from the rule's Lean doc comment and conformance examples (no second prose source, rule 5/6). A `concrete explain <rule>` command is new CLI surface: an owner question (one way per thing).
d. A message style guide: second person, no unexplained jargon, show the code, say what to do next. A hint appears only when it is certain to be correct (decided: a fix is offered only after recheck, auto-applied only if a lemma proves it meaning-preserving).
e. No cascades: the owner's item 12 stops at the first error per file. Is that enough (multiple files, errors after recovery, agent workflows)?
f. A quality gate: golden diagnostics (T-f) plus a model reviewer that scores every new or changed message against the style guide; a refusal without a reviewed golden fails.
The lexer and parser are writing refusals now, so the format is needed before slice 1.
