## Part A: owner decisions of 2026-11-08 (15:08 UTC, the 29 answers, "all yes"). Encode exactly these; they are decided.

**Item 18 (constant initializers; revises TYPE-22).** Initializers may use *fallible* primitive operations, within a *closed grammar*: no calls, no loops, no effects. Success is *kernel-checked*: every initializer is evaluated at compile time (used or not), and a constant whose evaluation fails, or runs out of fuel, is refused.
- Extend the initializer grammar with the fallible scalar operations Spec/Scalar.lean already defines, reusing those definitions (do not define a second arithmetic): the plain operations `plain` / `plainNeg` (add, subtract, multiply, divide, remainder, negation, shifts; failures `Overflow`, `DivisionByZero`, `InvalidShift`, OD114 division) and the fallible conversion `tryConvert`. At compile time a failure of any of them refuses the constant (it never becomes a trap). The `checked` forms return `Result<T, ArithmeticError>`, which is not a type of the current constant universe (`CTy`): do not widen `CTy` (that is an owner decision, see the module doc); list "checked forms in initializers need a Result constant type" under QUESTIONS instead.
- Keep the grammar closed: no calls, loops, effects, state, authority or target dependence (the target profile only where the scalar operations already depend on it, e.g. widths; say which).
- Evaluation becomes partial and fuel-bounded: `eval` returns a value, a failure (which operation, at which sub-expression) or out-of-fuel. Every operation still terminates; fuel bounds the evaluation as the decision says.
- Admission (`ConstsAdmitted`) becomes: the list types (as now) AND every initializer evaluates successfully within the fuel. A failure or fuel exhaustion refuses the constant, whether or not the constant is used anywhere. Make admission decidable so that `decide` (kernel reduction, never `native_decide`) checks a concrete program's constants: that is what "kernel-checked" means here.
- Restate the laws: `eval_total` no longer holds for the widened subset; replace it with (i) totality for the old fallible-free fragment (keep it, it is still true and useful), (ii) admitted ⇒ every constant has a value of its declared type (`evalConsts_sound`), (iii) admission ⇔ typed ∧ evaluates within fuel, with the refusal side naming the failing constant and its failure.
- Examples: Accepted: an initializer using division that succeeds (e.g. `100 / 7`) and an unused constant whose initializer succeeds. Refused: `1 / 0`, a signed overflow (`i8` `127 + 1`), an out-of-range shift, and an UNUSED constant whose initializer fails (refused although never used: this is the TYPE-22 revision). One example where fuel runs out (a fuel bound too small for a deep but finite initializer) is refused.
- Update the module doc comment: remove "a question for the owner, not decided here" about failing operations; cite "owner decision 2026-11-08, item 18 (revises TYPE-22)".

## Vacuity rule (owner, binding)
No law may hold because a guard or a definition makes it trivially true (for example a run-time re-check of the invariant inside the operation, a theorem that restates its definition, or a hypothesis that can never hold). For every law you add or change, give (a) a non-trivial instance: an example where its hypotheses hold, and (b) a planted counter-example: a mutated rule or a bad state that fails it, written as an `example` with a negation.
