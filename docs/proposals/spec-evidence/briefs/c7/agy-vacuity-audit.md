### 2. Detailed Findings

1. **`ConcreteSpec/Proofs/Leak.lean:523-545` — [blocker] [REAL DEFECT] `established_report_sound`, `empty_function_report_sound`, and `unestablished_report_sound` are vacuous and lack any unsound-report counter-example or connection to `run`.**
   - **Problem:**
     - `established_report_sound` (L523) plugs the exact expressions from the definition of `LineageReport.Sound` (`exit.requested - entry.requested`, `(exit.live : Int) - (entry.live : Int)`, `exit.functionPeak`) into the report's `Bound` limits and proves `x ≤ x` by `simp`. It also leaves `footprint` as `.notEstablished`, so `Bound.SoundOptional` is never positively exercised at all.
     - `unestablished_report_sound` (L540) sets all four `BoundStatus` fields to `.notEstablished`, making the antecedent `b.status = .boundEstablished` false in all four conjuncts (`False → ...`).
     - `empty_function_report_sound` (L532) checks `0 ≤ 0` on `entry = exit = Account.enter ⟨100, 0, 100, 0⟩` with no `run` steps.
     - None of the report theorems connect `entry` and `exit` via `run (m.set lineage (m lineage).enter) actions = some m'`, and there is no planted counter-example showing an unsound `LineageReport` (e.g., claiming a peak bound smaller than `exit.functionPeak`, or claiming `.boundEstablished` for `footprint` when `footprint = none`).
   - **Concrete fix:**
     - Replace `established_report_sound` and `empty_function_report_sound` with a theorem connecting `Account.enter` and `run` to `LineageReport.Sound`: given `m₀` with entry account `entry = (m₀ lineage).enter` and `run (Memory.set m₀ lineage entry) actions = some m'`, prove that any report whose established limits upper-bound `allocated lineage actions`, `(allocated lineage actions : Int) - freed lineage actions - resetBytes lineage actions`, and `(m' lineage).functionPeak` (plus a ` some fp` witness for `Bound.SoundOptional`) satisfies `LineageReport.Sound entry (m' lineage) (some fp) r`.
     - Provide a non-trivial multi-action instance where pre-entry `requested = 100, peak = 100`, the function allocates and frees bytes after `Account.enter`, and the function-local report establishes tighter bounds than the historical totals.
     - Add planted counter-examples: `¬ LineageReport.Sound ...` when an established bound under-reports `requested`, `netChange`, or `functionPeak`, and when `footprint` has status `.boundEstablished` with `footprint = none`.

2. **`ConcreteSpec/Proofs/Leak.lean:89-245` — [blocker] [REAL DEFECT] `Demo.secure_ni` and `Demo.secure_ct` are degenerate instances of `DelimitedReleaseNI` and `ConstantTime`: `start` never touches the secret or declassifies anything secret-dependent, and NI vs. CT are not separated.**
   - **Problem:**
     - `DelimitedReleaseNI` (`Spec/Leak.lean:155`) and `ConstantTime` (`Spec/Leak.lean:164`) are defined with the delimited-release premise `r₁.releases = r₂.releases` and `LowEquivalent L c₁ c₂`.
     - However, in `Demo.start` (`Proofs/Leak.lean:89`), the program is `body (.lit 7)` = `.seq (.prim none .release [.lit 0] ⟨0⟩) (.prim none .output [.lit 7] ⟨1⟩)`. Neither the release nor the output ever reads `.secret`! And `instrumentation.releases` (`Proofs/Leak.lean:145`) is hardcoded to emit `releaseZero` *only* on `some (.release, [0], _)`.
     - Consequently, `r₁.observations = [.output 7]` and `r₁.leakage = [.variableTime ⟨0⟩ [0], .variableTime ⟨1⟩ [7]]` hold unconditionally for every `s₁, s₂` without using `LowEquivalent`, `r₁.choices = r₂.choices`, or `r₁.releases = r₂.releases` (notice line 232 and line 242: `intro r₁ r₂ _ _ _` discards all three hypotheses!).
     - Furthermore, the module docstring (`Spec/Leak.lean:16`) states that `DelimitedReleaseNI` and `ConstantTime` are distinct claims, yet there is no example separating them (e.g., a program that satisfies `DelimitedReleaseNI` via a declassified secret release or public output while violating `ConstantTime` due to secret-dependent variable-time operands, or vice versa).
   - **Concrete fix:**
     - Change `instrumentation.releases` to emit a `Release` record carrying the actual evaluated operand `v` for any `some (.release, [v], site)`.
     - Make the positive `DelimitedReleaseNI` example actually release and output a secret-dependent value (e.g., `.seq (.prim none .release [.secret] ⟨0⟩) (.prim none .output [.secret] ⟨1⟩)`), so that `secure_ni` genuinely relies on the `r₁.releases = r₂.releases` hypothesis to conclude `r₁.publicObservations = r₂.publicObservations`!
     - Add a separating example that satisfies `DelimitedReleaseNI` (using the declassified release hypothesis `r₁.releases = r₂.releases` or outputting a constant) but fails `ConstantTime` (by passing `.secret` to a variable-time operation without releasing it, or branching on `.secret`), and conversely or alongside `secure_ct`.
     - Make `Labelling` non-trivial in `Demo` (or in a companion example) by having at least one public local or public store projection so `publicLocals` and `LowEquivalent` are exercised on `some` projections, with a planted counter-example where `¬ LowEquivalent labelling c₁ c₂`.

3. **`ConcreteSpec/Spec/Leak.lean:315-326` — [blocker] [REAL DEFECT] `WipeEvent` and `WipePreservation` have zero laws, zero non-trivial instances, and zero planted counter-examples.**
   - **Problem:** `WipeEvent` and `WipePreservation` are defined at the end of `Spec/Leak.lean` and never used, proved, instantiated, or counter-exemplified anywhere in `Spec/Leak.lean` or `Proofs/Leak.lean`.
   - **Concrete fix:** In `Proofs/Leak.lean`, add:
     - A compositionality/transitivity law for `WipePreservation` (e.g., two pass relations `R₁` and `R₂` that each satisfy `WipePreservation` compose to a pass `R₁ ∘ R₂` satisfying `WipePreservation`) and/or a law showing that an instrumentation step trace preserving wipes satisfies `WipePreservation`.
     - A non-trivial instance (e.g., an optimization pass that simplifies pure expressions while preserving `WipeEvent` statements) proved to satisfy `WipePreservation`.
     - A planted counter-example (a dead-store / erasure pass that elides a `WipeEvent` while preserving `publicObservations`) proved to satisfy observation preservation but `¬ WipePreservation`.

4. **`ConcreteSpec/Spec/Leak.lean:217,236` & `ConcreteSpec/Proofs/Leak.lean:416-426` — [major] [REAL DEFECT] `reset_conservation` is vacuous by runtime guard in `apply`, and both `free_conservation` and `reset_conservation` omit `functionPeak` conservation and planted counter-examples.**
   - **Problem:**
     - `Action.reset lineage released` carries `released : Nat`, and `apply` (`Spec/Leak.lean:236`) guards the transition with `if released = (m lineage).live then some (Memory.set m lineage (m lineage).reset) else none`. Then `reset_conservation` (`Proofs/Leak.lean:416`) claims `(m' lineage).live = (m lineage).live - released`. Because `Account.reset` sets `live := 0`, `(m' lineage).live = (m lineage).live - released` holds *only* because `apply` checked `released = (m lineage).live` in the guard!
     - Both `free_conservation` (L402) and `reset_conservation` (L416) omit `(m' lineage).functionPeak = (m lineage).functionPeak`, contradicting the module docstring at `Proofs/Leak.lean:17-19` (*"Free and reset conserve cumulative history and both historical and function-local peaks"*).
     - `apply_peak_monotone` (L478) and `run_peak_monotone` (L509) likewise omit `(m lineage).functionPeak ≤ (m' lineage).functionPeak`.
     - There is no planted counter-example for `reset` with an invalid `released` count, nor a counter-example showing `Account.alloc_zero` fails when `¬ a.WF`.
   - **Concrete fix:**
     - Add `(m' lineage).functionPeak = (m lineage).functionPeak` to both `free_conservation` and `reset_conservation`, and add `(m lineage).functionPeak ≤ (m' lineage).functionPeak` to `apply_peak_monotone` and `run_peak_monotone`.
     - In `reset_conservation`, state `(m' lineage).live = 0 ∧ released = (m lineage).live` explicitly (rather than disguising `0` as `(m lineage).live - released`), or make `Action.reset (lineage : LineageId)` not require a pre-guessed `released` count and define `resetBytes` over `(m, actions)` so the conservation law is not dependent on a caller-supplied guard check.
     - Add planted counter-examples in `Proofs/Leak.lean`:
       - `apply Memory.empty (.reset ⟨0⟩ 1) = none`
       - `∃ a : Account, ¬ a.WF ∧ a.alloc 0 ≠ a` (showing the `a.WF` hypothesis of `Account.alloc_zero` is necessary and non-vacuous)
       - `∃ m m' a l, apply m a = some m' ∧ ¬ (m l).live ≤ (m' l).live` (showing `.live` is not monotone, unlike `.peak` and `.functionPeak`).

5. **`ConcreteSpec/Proofs/Exec.lean:530-617` — [major] [REAL DEFECT] The 10 new `*_refused` theorems in `Proofs/Exec.lean` are definition-unfolding restatements (and `continuation_refused` is a trivial `Option` lemma) with no instances or counter-examples for `.enter`, `.leave`, or `.bind` refusal.**
   - **Problem:**
