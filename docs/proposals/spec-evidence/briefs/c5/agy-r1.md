1. **`ConcreteSpec/Spec/Own.lean:274` — MAJOR — REAL DEFECT: `CallState` lacks a well-formedness invariant preventing duplicate or stale `pending` entries**
   - **Problem**: `passDown` (lines 281–286) appends `(parameter, ⟨s.own.nextLoan⟩)` to `s.pending` without checking that `parameter` is not already in `s.pending`. Meanwhile, `callLife` on `.enter` (lines 291–297) requires `adoptDown own s.pending`, which demands `(args.map Prod.fst).Nodup ∧ (args.map Prod.snd).Nodup` and that every `e.2` in `s.pending` exists in `own.loans` with `pendingArgument = true`. Furthermore, if `callLife` handles `.leave` while `s.pending` is non-empty, `endLocals` will end any pending argument loans created in the departing frame, leaving dangling `LoanId`s in `s.pending`. Because `CallState` has no `WellFormed` predicate (unlike `State`), `passDown_preserves` (`Proofs/Own.lean:221`) and `callLife_preserves` (`Proofs/Own.lean:231`) only prove `WellFormed t.own` and do not guarantee that `pending` remains synchronized with `own.loans` (where `pendingArgument = true`) or has unique parameter names.
   - **Concrete fix**:
     1. In `passDown` (`Spec/Own.lean:281`), guard against duplicate parameter bindings: check `if s.pending.any (·.1 == parameter) then none else ...`.
     2. In `callLife` (`Spec/Own.lean:290`), require `s.pending = []` for non-`.enter` events (or at least for `.leave` / `.drop`), or define `CallState.WellFormed (s : CallState) : Prop` asserting `s.own.WellFormed`, `(s.pending.map Prod.fst).Nodup`, `(s.pending.map Prod.snd).Nodup`, and `∀ l ∈ s.own.loans, l.pendingArgument = true ↔ l.id ∈ s.pending.map Prod.snd`, and prove its preservation across `passDown` and `callLife`.

2. **`ConcreteSpec/Spec/Own.lean:150` — MAJOR — REAL DEFECT: `borrow` allows borrowing directly from a root while it has a `pendingArgument` loan, or `passDown` lacks an direct-owner variant**
   - **Problem**: In `Spec/Own.lean:281`, `passDown` only accepts `(source : LoanId)` and calls `reborrow s.own source [] l.mode`. In Concrete (Q3.2, OD23), downward call arguments can be borrowed directly from an owning variable (`&x` or `&mut x`) as well as reborrowed from an existing view (`r`). Under the current API, to pass `&mut x` to a call, the caller must first `borrow` `x` (producing a caller-frame loan `i` with `pendingArgument = false`) and then `passDown` `i` (producing a child loan `j` with `pendingArgument = true` that is adopted by the callee). When the callee returns (`leave`), `j` is ended by `endLocals`, **but the caller-frame loan `i` remains active** after the call returns! The caller's owner `x` stays frozen after the call unless an extra `endLoan` is manually issued.
   - **Concrete fix**: Add `passOwnerDown (s : CallState) (p : Hybrid.Place) (path : List Projection) (m : Mode) (parameter : Var) : Option CallState` (which opens a loan directly with `pendingArgument = true` so that adopting it into the callee activation causes `leave` to end the loan completely upon return), and add its preservation theorem in `Proofs/Own.lean`.

4. **`ConcreteSpec/Proofs/Own.lean:38` — MINOR — PREFERENCE: Preservation theorems do not require `WellFormed s` only because `validate` re-checks the entire state at run time**

Consequently, `move_preserves`, `borrow_preserves`, etc. in `Proofs/Own.lean` and `Proofs/Grant.lean` just unpack `validate_iff` in 4 lines instead of proving that the transition preserves `WellFormed s` structurally from `hs : WellFormed s` (i.e., that when the guard succeeds on a `WellFormed` state, `validate` *cannot* fail). While the theorems as stated (`f s = some t → WellFormed t`) are non-vacuous (as witnessed by the `decide` examples), they do not prove that `validate` inside each operation is redundant when starting from a `WellFormed` state.
   - **Concrete fix**: Either prove a progress/completeness lemma for the core transitions (e.g., showing that if `WellFormed s` and the operational guard holds, the candidate state before `validate` satisfies `WellFormed`, so `validate` never causes spurious stuckness), or note explicitly in `Proofs/Own.lean` and `Proofs/Grant.lean` that `validate` is part of the executable transition definition by design.
