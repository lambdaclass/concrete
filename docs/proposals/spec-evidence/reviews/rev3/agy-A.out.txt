1. **minor** — `ConcreteSpec/Spec/Exec.lean:275-282` (`onRes`, `step`, `evalArgs`) and `ConcreteSpec/Spec/Outcome.lean:69-70`
   - **Problem:** When a compound operand or argument list (`evalArgs`) traps at a sub-operand after an earlier sub-operand has mutated the instrumentation state (e.g., `call none f [.move a, .fail .overflow]`), `Res.trap` does not carry the intermediate `Store`, and `onRes` restores the pre-operand `st` in `.trapped kd site L st k`. Because `.trapped` is strictly terminal (`step_trapped`), this makes no difference to subsequent steps, and `Outcome.lean:69-70` says an operand has no effects. However, two comments are slightly out of sync or potentially fragile for C5/C8:
     1. `Outcome.lean:69-70` says "An operand is evaluated without effects (Core is in A-normal form, Q9.1), so these are its only results", whereas `Exec.lean:88-91` and `112` now instantiate `Res (Val × Store)` to thread instrumentation state.
     2. If C5 or C8 ever inspects the `store` field of a terminal `.trapped` configuration (for example, to assert an invariant on moved/borrowed state at the trap point), rolling back the instrumentation state of already-evaluated arguments in `evalArgs` would hide moves that happened before the trapping argument.
   - **Concrete fix:** Either document explicitly on `onRes` (`Exec.lean:275-276`) and `Outcome.lean:69-70` that post-trap `Config.store` is unused because `.trapped` is terminal (and mention in `Outcome.lean` that `V` may pair the value with instrumentation state), or carry `Store` in `.trap` / thread it in `evalArgs` if C5/C8 will inspect the trapped configuration's instrumentation store.

2. **minor** — `ConcreteSpec/Spec/Exec.lean:336-337`, `354`, `391-392` (`step` for `.call` and `.done`/`Frame.ret`, and `enter`)
   - **Problem:** Two subtle points around function entry/exit and C5 ownership instrumentation:
     1. On function entry (`Exec.lean:336-337` and `392`), the callee's parameter bindings are `(fn.params.map Prod.fst).zip vs`, while `st'` (which holds the caller's instrumentation state, as seen in `Proofs/Exec.lean:515` where `demo_log_completes` requires `h : Demo.x ∉ st.moved` on the callee's parameter `Demo.x`!) is passed straight into the callee without clearing or scoping `Var` instrumentation for the callee's parameters. In the Demo, `logFn`'s parameter `Demo.x` collides with any caller `Demo.x` in `st.moved`. Even with globally fresh `Var` IDs (Q9.1), recursive calls to the same `Fn` reuse `fn.params` `Var` IDs (`[(x, .int)]`), so a recursive call that moves its parameter `x` in frame 1 will leave `x ∈ st.moved` in frame 2!
     2. When a function body completes by falling off the end (`.done` reaching `.scope fn.block ...` then `.ret dst caller`, `Exec.lean:354`), `step` transitions from `.done` at `.ret dst caller` to binding `O.unitVal` in `caller`. If `fn` had a non-`Unit` return type and fell off the end (which the checker rejects, but `Step` defines operational behavior for), it silently fabricates `O.unitVal` instead of being `.stuck`. Conversely, in `enter` (`Exec.lean:391-392`), there is no `.ret` frame, so a `Unit`-returning `main` that falls off the end finishes with `Final.normal`, whereas `return ()` finishes with `Final.returned O.unitVal`.
   - **Concrete fix:**
     1. For C5 compatibility across recursive calls, note in `Operands` (`Exec.lean:87-92`) or `Fn` that either C5's instrumentation state is keyed by call-frame/activation ID (or `Operands` provides call-entry / scope-exit hooks on `Store`), and in `Demo` avoid reusing `Demo.x` or note why `demo_log_completes` needed `Demo.x ∉ st.moved`.
     2. In `Exec.lean:354`, either document that the checker ensures only `Unit`-returning functions fall through to `.ret` (and consider whether `enter` should wrap or document the `Final.normal` vs `Final.returned unitVal` distinction for `Unit` entrypoints), or check/document it explicitly.

3. **minor** — `ConcreteSpec/Proofs/Exec.lean:329-339` (`cleans_runs_plan`)
   - **Problem:** The docstring says "A cleanup runs exactly the plan: the calls of `plan pre`, in order, each with its scope's locals, and nothing else." The theorem proves the forward direction (`Cleans P pre L st tr st' → RunsEach P (planWith pre L) st tr st'`), which shows that `Cleans` implies `RunsEach`, stabilized by `planWith`. However, because `Cleans` is the hypothesis of `unwind_runs_plan`, a consumer who has proved `RunsEach P (planWith pre L) st tr st'` (or wants to know the two characterizations are equivalent) also needs the converse (`RunsEach P (planWith pre L) st tr st' → Cleans P pre L st tr st'`), or an `iff` (`Cleans P pre L st tr st' ↔ RunsEach P (planWith pre L) st tr st'`).
   - **Concrete fix:** Strengthen `cleans_runs_plan` in `ConcreteSpec/Proofs/Exec.lean:331` to an `iff`:
     `theorem cleans_iff_runs_plan : Cleans P pre L st tr st' ↔ RunsEach P (planWith pre L) st tr st'` (splitting `RunsEach` across `++` for the `.scope` case).

4. **nit** — `ConcreteSpec/Spec/Exec.lean:247-250` (`bindDst`) and `318-321` (`Stmt.bind` vs `Stmt.assign`)
   - **Problem:** `Stmt.bind` prepends `(x, v) :: L` (`Exec.lean:319`), `Stmt.assign` updates an existing entry in `L` (`Exec.lean:321`), and `bindDst` (`Exec.lean:250`, used by `.call` and `.prim`) prepends `(x, v) :: L` like `Stmt.bind`. The docstring on `Stmt` (`Exec.lean:119-120`) explains `bind` vs `assign`, and `Stmt.call`/`Stmt.prim` (`Exec.lean:146-150`) say "bind the result to `dst`", which matches `bindDst` introducing a fresh binding in A-normal form, but `bindDst`'s docstring (`Exec.lean:246`) doesn't mention that `dst` is a fresh local binding (like `Stmt.bind`, not an assignment to an existing local).
   - **Concrete fix:** Clarify in the docstring of `bindDst` (`Exec.lean:246`) and `Stmt.call`/`Stmt.prim` (`Exec.lean:146-150`) that `dst : Option Var` binds a fresh local in the current scope (just like `Stmt.bind`).
