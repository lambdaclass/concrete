• No blockers found, and `decodePtr` remains unchanged. The following issues need changes.

  1. **Major — REAL DEFECT — `ConcreteSpec/Spec/Memory.lean:63`, `ConcreteSpec/Spec/Memory.lean:169`, `ConcreteSpec/Spec/Memory.lean:278`**  
     `Ptr.addr` is an unrestricted `Nat`, so operations accept addresses outside the target’s address width. On a well-formed 8-bit target, address `256` passes a zero-byte load with alignment 1 and null 0. Similarly, `encodePtr` truncates `256` to byte `0`, while `decodePtr` reconstructs `256` from the fragment metadata. Thus the pointer round trip does not establish that the encoded address denotes the pointer’s address.  
     **Fix:** introduce target-relative pointer validity (`addr < 2 ^ tgt.addrBits`, together with address-space validity), or make valid pointers intrinsic to the representation. Thread it through zero-byte accesses and pointer encoding/round-trip premises without changing `decodePtr`.

  2. **Major — REAL DEFECT — `ConcreteSpec/Spec/Memory.lean:140`**  
     `Memory.Fits` never checks `x.space ∈ tgt.spaces`. Consequently, `linuxX8664` permits allocation in arbitrary undeclared spaces such as `⟨99⟩`, despite `Target.spaces` defining the spaces the target has. Hybrid materialization inherits this behavior.  
     **Fix:** require the candidate block’s space to belong to `tgt.spaces` in `Fits`, and include the corresponding condition in `Memory.WellFormed` so manually constructed memories cannot bypass it.

  3. **Major — REAL DEFECT — `ConcreteSpec/Proofs/Memory.lean:190`**  
     Well-formedness preservation is proved only for allocation. There are no corresponding laws for `free` (`Spec/Memory.lean:159`), `store` (`Spec/Memory.lean:192`), or `expose` (`Spec/Memory.lean:204`). Since central theorems such as `store_load` and `Hybrid.write_read` require well-formedness, clients cannot compose the supplied laws across ordinary operation sequences without rebuilding these proofs themselves.  
     **Fix:** add `empty_wellFormed`, `store_wellFormed`, `free_wellFormed`, and `expose_wellFormed`, then derive preservation for hybrid writes, materialization, and exposure.

  4. **Major — REAL DEFECT — `ConcreteSpec/Proofs/Hybrid.lean:95`**  
     The general first-materialization law is missing. `materialize_projection` proves only that the cell becomes materialized; neither it nor `rep_roundtrip` proves that reading immediately after materializing a structured value returns that same value. The examples do not cover this generically: the main example overwrites the initial boolean before reading it. A defect in initial integer encoding could therefore escape the principal hybrid laws.  
     **Fix:** prove, under initial memory well-formedness and a structured-cell hypothesis, that successful first materialization gives `st'.read tgt p = some v`; add a direct integer materialize/read example.

  5. **Minor — REAL DEFECT — `ConcreteSpec/Spec/Hybrid.lean:98`**  
     The documentation calls `places` a finite map, but `Place → Option Cell` also represents infinite maps. The examples at lines 160 and 182 use `fun _ => some …`, which are explicitly infinite. This weakens the interface for C5 lifecycle operations that may need finite domains or iteration.  
     **Fix:** use the repository’s `AList Place Cell`, or document the map as potentially infinite and state any finite-domain invariant separately.

  6. **Minor — REAL DEFECT — `ConcreteSpec/Spec/Hybrid.lean:28`**  
     `Hybrid.Ty`, `Value`, `Value.ty`, and `Value.Valid` duplicate the integer/bool portion of `Const.CTy`, `CVal`, `CVal.ty`, and `CVal.Valid` at `ConcreteSpec/Spec/Const.lean:59-81`. This creates two scalar-value interfaces that C1, constant evaluation, and ownership instrumentation must bridge.  
     **Fix:** factor the shared scalar type/value definitions into `Scalar.lean`; let the constant-only universe extend them with `unit`, and have Hybrid use the shared definitions.
