### 3. Assessment of Writer's Open Questions

1. **Activation targets (`reborrowAt`: restrict to current activation + new callee?)**
   - **Assessment**: **Restrict `reborrow` to the current activation (`s.frames.head?`), and remove arbitrary activation targeting from the public primitive API.**
   - **Reasoning**: Under `passDown` + `adoptDown` (OD23), downward call arguments are reborrowed in the *caller's* activation during left-to-right argument evaluation (`reborrow` at `f.id` with `pendingArgument := true`) and then *adopted* into the new callee activation on `enter` (`adoptDown` rewrites `activation := f.id`). Nothing in the C1/OD23 call protocol needs to specify a target `activation : Nat` at reborrow time except the standalone legacy helper `enterDown`. Therefore, `reborrowAt` should either be made `private` (an internal helper for `reborrow` and `enterDown`) or restricted so that loans can only be created in `s.frames.head?` and moved to a newly pushed callee frame by `adoptDown`. Allowing arbitrary `activation < s.nextActivation` permits targeting already-popped (historical) frame IDs or outer caller frames (upward reborrowing, violating Q3.2).

2. **Direct owner arguments (call-duration root loan vs. explicit caller borrow scope)**
   - **Assessment**: **Introduce a call-duration root loan (`passOwnerDown` or allowing `pendingArgument := true` on root loans created for call arguments).**
   - **Reasoning**: In surface Concrete, passing `&x` or `&mut x` directly to a function `f(&mut x)` is the most common way to lend an owner across a call, and the freeze of `x` must last only for the call (starting when the argument is evaluated left-to-right per OD23, and ending when `f` returns). If the caller had to open a normal lexical `borrow` first and then `passDown` a child loan, the caller's root loan would outlive the call until an explicit `endLoan` in the caller. Allowing a call-argument root borrow (which sets `pendingArgument := true` with `parent := none`, is adopted into `f.id` by `adoptDown`, and is automatically ended by `endLocals f.id` inside `leave`) cleanly models `f(&x)` / `f(&mut x)` using the exact same `adoptDown` + `leave` machinery without requiring synthetic post-call cleanup statements in C1. (Note: if root loans can be pending arguments, `WellFormed`'s clause `l.pendingArgument = true → l.parent.isSome = true` simply drops or becomes `l.parent = none ∨ l.parent.isSome`).

3. **C1 erasure form (successful-step simulation with stuck equivalence conditional on checker safety)**
   - **Assessment**: **Endorse the two-part formulation: (a) unconditional forward simulation for non-stuck instrumented runs, and (b) full outcome equivalence conditional on checker safety (or no-permission-refusal).**
   - **Reasoning**: As `erasedMoveRun` in `ConcreteSpec/Spec/Own.lean:534-547` proves, ownership and brand instrumentation acts as a dynamic permission monitor that turns unsafe operations (use-after-move, conflicting borrows, escaping brands) into `.stuck`. Erased execution does not track permissions and continues executing. Therefore:
     - **Part A (Soundness of Erasure / Forward Simulation)**: For any C1 execution where the instrumented run terminates in `.final o` (returned, trapped, etc.) or takes a valid step, the erased run takes the exact same step and produces the exact same `.final o` and observable trace. This can and should be proved in C1/C5 integration without waiting for C9.
     - **Part B (Completeness / Stuck Equivalence)**: If a program is accepted by the C9 type/borrow checker (which guarantees the instrumentation never refuses a step on reachable states), then the instrumented run never gets `.stuck` on permission checks, so instrumented and erased runs have identical outcomes (including `.stuck` if and only if the underlying concrete semantics gets stuck).
