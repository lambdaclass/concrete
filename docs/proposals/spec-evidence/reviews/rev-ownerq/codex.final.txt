1. **question A, background — major, REAL DEFECT.** “Real elaborated programs always…” and “no compiled program behaves differently today” are unsupported. Elaboration, including conversion of names to identities, remains an open obligation in ConcreteSpec/README.md:49-58. The supplied example establishes disagreement on manually constructed locals, not its reachability from source. **Fix:** say: “The two evaluators disagree on this constructed input. Whether elaboration can produce it has not been established.” Obtain elaborator evidence before claiming compiled programs are unaffected.

2. **question A, option 1 — major, REAL DEFECT.** “One change” and “rename-invariance proofs become trivial or are deleted” understate the migration. Assignment both looks up and updates locals; scope restoration compares whole variable records; move tracking also uses those records. See ConcreteSpec/Spec/Exec.lean:259-264,363-368,934-948 and ConcreteSpec/Spec/Basics.lean:26-39. Numeric renaming still requires an injectivity argument, and presentation invariance remains a useful proved property: ConcreteSpec/Proofs/Prim.lean:13-53,86-127. **Fix:** specify one semantic identity representation used throughout lookup, update, scope restoration and ownership tracking, with corresponding law migrations. Preserve presentation-invariance laws rather than promising their deletion. The diagnostics schema can remain unchanged if the existing fields and types are retained; renaming them would change the interface, per ConcreteSpec/Spec/Ident.lean:28-44. Make that condition explicit.

3. **question A, option 2 — major, REAL DEFECT.** “Every proof that renaming is harmless needs a ‘renamed consistently’ premise” conflates numeric renaming with changing hints. Numeric renaming already applies a bijection consistently while preserving hints: ConcreteSpec/Spec/Prim.lean:25-30,57-72. Conversely, arbitrary hint changes can collapse distinct number-and-name identities; consistent application alone does not prevent that. **Fix:** present its strongest version: “Use composite identity everywhere. Numeric bijective-renaming laws remain; hint-renaming laws require preservation of composite-key distinctions, or restriction to inputs with unique numbers and consistent hints. Revise the presentation-only contract and establish the elaboration invariant.”

4. **question A, option 3 — major, REAL DEFECT.** Calling a checked bridge inherently contrary to the one-owner rule misstates policy. Checked views are expressly permitted by docs/PHILOSOPHY.md:68-73. **Fix:** offer an authoritative identity model with a proved alternative implementation over an explicitly enforced admissible domain. State the actual cost: proving and preserving name consistency and numeric uniqueness across producers and transitions. Recommend option 1 because it removes those premises and spelling dependence, consistent with docs/PHILOSOPHY.md:124-129, rather than declaring the alternative structurally forbidden.

5. **question B, option 1 — major, REAL DEFECT.** The proposed obligation cannot simply be checked “once” on every adapter: the current well-formedness predicate has no initial configuration parameter, and the launcher neither requires that predicate nor any initial-state equality. It accepts an arbitrary configuration. See ConcreteSpec/Spec/Observe.lean:576-589,639-647. **Fix:** require a checked launch configuration whose projected store equals the declared starting state, and make the launcher consume that evidence. Include migration of the refusal theorem, which currently promises the projected store without that premise: ConcreteSpec/Proofs/ObserveReport.lean:212-227. Distinguish a proof obligation from executable rejection; the proposed predicate alone implements no rejection mechanism.

6. **question B, options 2 and 3, recommendation — major, REAL DEFECT.** Option 3 is a knowingly defective placeholder, while option 2’s strongest benefit is omitted. A per-launch authoritative starting state supports different initial stores under one event signature and reports the actual pre-execution state. The current interface separates the signature’s starting-state field from the adapter’s store projection: ConcreteSpec/Spec/Observe.lean:34-44,454-458. Neither “unchanged” nor the one-source rule alone decides which should own initialization. **Fix:** contrast two coherent designs: a fixed declared state with checked launch configurations, and an explicit per-launch state shared by both launchers. Explain whether multiple initial states should require different signatures. For option 2, include signature constructors, the generic-launch example, and proof-side transformation controls in migration costs: ConcreteSpec/Spec/Observe.lean:711-717,798-799; ConcreteSpec/Proofs/ObserveTransform.lean:36-72.

7. **question B, evidence — minor, REAL DEFECT.** The supplied execution computes the generic launcher and the adapter projection separately; it does not execute the program launcher with the mismatched initial store. The implementation supports the predicted discrepancy, but the demonstration is incomplete: ConcreteSpec/Spec/Observe.lean:639-647. **Fix:** have the coordinator execute both launchers using the same signature and a concrete configuration projecting to 1, with missing grants, and show the complete refusal results. Retain “would report” until that run exists.
