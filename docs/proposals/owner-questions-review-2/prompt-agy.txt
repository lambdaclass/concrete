## What Concrete is for

**Concrete is a fully proven systems programming language with no garbage collector, where you can
know everything a program does: what it does, what it may touch, whether it can fail or stop, and
what is proved about it.** "Fully proven" means compiler correctness proved end to end, with every
unproven step named as an explicit assumption and never silently trusted, and a program's own
correctness proved by Lean theorems about it. This states the project's goal: each guarantee holds
only as its evidence lands, and native claims remain conditional on their named assumptions
([decision](decisions.md#decided-project-core-statement)).

Concrete is a small systems language for code that must be reviewed, audited, bounded and proved:
no garbage collector and no hidden runtime, linear ownership, second-class references, and
authority that is visible in every signature. Its aim is that a reader can answer "what does this
code do, what may it touch, and what is actually proved about it" from the source, the compiler's
reports and the Lean theorems, without trusting anything that is not named. Lean 4 is the language
the semantics and proofs are written in and the language the compiler is built in; Concrete itself
stays a systems language, not a proof assistant.

Most Concrete code is expected to be written by language models, not typed by hand. What matters
is that everything is checkable and easy to understand: the cost that counts is the cost for a
reviewer, an auditor or a checker to understand what code does and what it may touch. Rule 4
draws the consequence for verbosity.

## The rules

Each rule states what holds and why. Its history is in the changelog and the decision record.

1. **Pick the best long-term structural solution.** A design question is answered by the structure
   that removes the whole class of problem, not by the smallest local patch, and once that answer is
   known it is chosen rather than offered as one option among several. *Why:* a patch fixes one
   instance and leaves the class to recur; the language is still small enough to change shape.

2. **One form per situation.** There are never two ways to write one thing. A second spelling, an
   alias or a convenience form beside an existing one is removed, not added. *Why:* every extra form
   is one more thing a reader, a checker and a proof must cover, and two forms drift apart. The
   decided removals are listed in [OD61](decisions.md#od61) and the entries it names.

3. **The most transparent long-term option wins.** Between two designs, prefer the one that leaves
   nothing for the reader to reconstruct: no hidden control flow, data flow, allocation, dispatch,
   authority or cleanup. *Why:* Concrete's value is that behaviour can be read off the source.

4. **Verbosity never argues against a clearer or safer design.** Writing more is acceptable when it
   makes behaviour, authority or failure visible. "It is longer" is not a reason to reject a
   design; "it hides something" is. *Why:* most code is now written by tools, where writing explicit
   forms is cheap and reviewing them is the expensive part.

5. **Every fact once.** Every fact that affects behavior or authority has exactly one authoritative
   definition, at a place the reader can find from the use site. Views checked against that
   definition (a signature, a compiler report, a derived table or registry) and explanatory
   examples are not second definitions. A restated fact that nothing checks (a size copied into a
   constant, a rule copied into a second document, a capability implied rather than declared) is a
   defect waiting to drift. This document is itself an instance: other documents link here.

6. **Lean is the specification.** The language's syntax, typing, ownership, effects and semantics
   are defined in Lean. Each rule is a readable definition with a plain-words doc comment and its
   conformance examples, and the reference interpreter is built from those definitions. No prose is
   generated from them. Machine views (the rule registry, rule IDs, manifests) are derived from them
   and checked for staleness. A guide may teach and link the rules but states none of its own. Until
   a rule lands in Lean, its prose chapter states the decided rule, and the chapter retires once its
   rules are covered
   ([Lean-source decision](archive/roadmap-2026-11/ROADMAP_DECISIONS.md#2026-11-01--lean-as-the-only-source),
   [revised 2026-11-04](archive/roadmap-2026-11/ROADMAP_DECISIONS.md#2026-11-04--lean-is-the-specification)). *Why:* one
   definition that machines check cannot silently disagree with itself, and a second prose
   rendering would be a second text to keep in step.

7. **Systems first, not theorem-prover first.** Source code reads as systems programming. Proofs
   attach to real Concrete functions through the semantics, not to a parallel reimplementation.
   *Why:* the point is evidence about the code that runs.

8. **No hidden runtime.** No garbage collector, no hidden reference counting, no hidden scheduler or
   executor, no life before `main`. What the target does at startup, at shutdown and on a trap is a
   named entry in the target's table. *Why:* memory, time and authority behaviour must be auditable
   and boundable.

9. **Ownership is linear, not affine.** A non-Copy value is used exactly once; it is never dropped
   silently at the end of a scope. Copy means "may be duplicated", nothing more. `_` names an unused
   binding and never discards a linear value, a `Result` or an `Option`
   ([OD62](decisions.md#od62), [OWN-5](../legacy/docs/spec/ownership.md#OWN-5)). Cleanup is an explicit
   consuming operation. *Why:* every resource has one visible owner and one visible end.

10. **References are second-class.** A reference may be passed down into a call or held inside a
    borrow block; no function, trusted or not, returns one and no value stores one
    ([REF-1](../legacy/docs/spec/references.md#REF-1), [REF-3](../legacy/docs/spec/references.md#REF-3)). Raw pointers, used
    in `trusted` code or under `with(Unsafe)`, are the only escape, and every use carries stated
    validity premises; the full raw-memory taxonomy is still
    [undecided](decisions.md#core-unsafe-premises). *Why:* scoped access
    needs no lifetime language, and the checker and the proofs stay local.

11. **Authority and trust are visible.** A function's permissions are declared in `with(...)`; a
    resource is a value it holds; an operation on a resource needs both. Nothing discharges or hides
    an operational capability, `trusted` and `with(Unsafe)` included, and there are no umbrella
    capabilities ([authority rules](decisions.md#decided-2026-11-02-authority)). *Why:* a
    reviewer reads what a function may do from its signature alone.

12. **Trust boundaries are honest.** Every claim says which of these it is: enforced by the compiler,
    reported by analysis, proved in Lean, or assumed at a named source, backend, toolchain or target
    boundary. Being listed in the trusted base proves nothing; an unknown is never reported as a
    reassuring default ([ABSENCE_IS_NOT_A_FACT.md](../legacy/docs/project/ABSENCE_IS_NOT_A_FACT.md)). New kinds of fact
    (frames, dependencies, ghost state, resource bounds) are reported through the one obligation and
    evidence ledger, never a parallel system. *Why:* evidence that overstates itself is worse than
    none.

13. **The compiler owns semantic identity.** A name, a link symbol or a restated constant is a
    representation of an entity, never the entity. Every pass preserves an entity's identity or
    creates a checked derivation from it, and identity claims are tested structurally, not by
    observed values. *Why:* using a representation as identity, and re-interpreting it in a later
    pass, is the single largest class of past compiler defects. (Older documents and comments
    call this "principle 12".)

14. **Artifact-first auditability.** The compiler emits facts, evidence and replay commands that
    people, CI and tools consume directly. Auditing never means reading the compiler's source.
    *Why:* an audit that depends on the auditor's reading of the implementation is not repeatable.

15. **A small analyzable core over feature growth.** A smaller language with strong boundaries
    beats a larger one with weaker analysis. Removing a feature is an improvement when what remains
    is more coherent; each refusal makes the rest easier to check, teach and prove. *Why:* every
    feature is paid for in grammar, checker, semantics, proofs and review.

16. **Predictable execution and a separable core.** Recursion, loop bounds, allocation, blocking and
    foreign calls stay visible, so a bounded, analyzable core can be told apart from an effectful
    shell, and writing code that way is natural. Before a program runs, every function has
    termination evidence with its premises, or a report naming the explicitly permitted unresolved
    obligations: every loop, recursive cycle, indirect call and blocking or foreign boundary either has termination
    evidence or carries a written permission at that source, which every report traces to its
    callers. Recursion depth, stack use, allocation, blocking, foreign calls and possible aborts are
    reported per function with their evidence, and a module or project policy may require them;
    these are reported facts, not function categories
    ([decision](decisions.md#decided-project-no-hidden-traps), 2026-11-06). *Why:* resource bounds
    and proofs need a core they can reach, and an unexplained infinite loop is a hidden behaviour.

17. **Real programs test the shape.** A design is validated by serious workloads, not by thought
    experiments alone, and a refused or deferred feature reopens only on such evidence. *Why:*
    hypothetical convenience is not a cost; measured pain is.

18. **No hidden traps.** Accepted safe code has no reachable implicit language trap: every operation
    that could fail at run time carries checked evidence that it cannot, or its failure is handled by
    a branch written in the source. An explicit `abort()` remains terminal behaviour and is reported
    transitively; resource exhaustion and foreign behaviour are named target and trust premises.
    Evidence comes from a small decidable checker proved correct in Lean, contracts whose evidence is
    closed, and Lean theorems, never from an unpredictable solver
    ([decision](decisions.md#decided-project-no-hidden-traps), 2026-11-06). *Why:* an inserted trap
    is an exit the reader of the operation cannot see, which rule 3 refuses for the same reason
    exceptions are refused.

## When rules conflict

**Decided by the owner on 2026-11-05** (row P2, [record](decisions.md#decided-project-priority)). When two rules pull in different directions, the earlier
item in this order wins:

1. soundness and provability, which includes honest trust boundaries (rule 12) and compiler-owned
   semantic identity (rule 13): a claim that overstates its evidence, or an entity known only by
   its spelling, is unsound;
2. transparency: nothing hidden, and every claim backed by an artifact a reader can inspect and
   replay (rules 3, 8, 11, 14);
3. a single source of truth: one authoritative definition per fact (rule 5);
4. explicitness at the use site;
5. brevity.

The third item is read with rule 5's definition: every fact that affects behavior or authority has
one authoritative definition, at a place the reader can find from the use site. So "write it once"
and "show it at the use site" agree whenever the use site can reach that definition, directly or
through a checked view such as a signature or a report; a fact that can be found only by searching
the whole program fails both.

**This order guides choices that are still open. It never reopens a decided rule.** The owner's
answers in [decisions.md](decisions.md) stand as recorded, whatever this order would
suggest; changing one is a new owner decision. When the order argues for changing a decided rule,
the change goes to the owner as a proposed revision and the decided rule stands meanwhile. For
example, type arguments are inferred from the checked argument types
([OD46](decisions.md#od46)), and that stands. Capability arguments were inferred the same
way ([OD45](decisions.md#od45), [OD87](decisions.md#od87)) until the owner
approved, on 2026-11-05, the revision that writes them on every capability-polymorphic call,
checked against the callee, because a call's authority should be read rather than solved for
([revision](decisions.md#decided-2026-11-05-revisions)).

## Admission test

A proposed language feature, compiler feature or borrowed idea is admitted only if every question
below has a good answer. Each question is a rule above applied to the proposal; failing one is
grounds for rejection.

1. **One form?** Does it add a second way to do something already expressible? (rule 2)
2. **Visible?** Does it expose ownership, effects, dispatch, layout, allocation or control flow, or
   hide work behind familiar syntax? (rules 3, 8)
3. **One fact, one place?** Is every fact it introduces written once and findable from the use site?
   (rule 5)
4. **A simple invariant?** Can it be stated as one Lean judgment without "except when" clauses, and
   does it elaborate into simpler Core forms? (rules 6, 15)
5. **Declaration-level and phase-separated?** Does it keep cross-module dependence on declarations
   and summaries, never on another module's bodies, and early phases independent of later semantic
   information? (rule 15)
6. **Static or explicitly indirect dispatch?** Is every call target known at compile time or visibly
   indirect at the call site? (rule 3)
7. **Predictable code?** Can a reader form a rough model of the generated work from the source?
   (rule 16)
8. **One owner?** Does exactly one pass or judgment own it, with one diagnostic when it fails? (rules
   5, 13)
9. **Authority intact?** Does every effect still appear in `with(...)` and every resource as a
   value, with no way to hide either? (rule 11)
10. **Through the contract boundary?** Do its safety, behaviour, effects, failure modes and resource
    consequences appear in summaries and obligations, rather than disappear at a function boundary?
    (rules 12, 14)
11. **Fails visibly?** Does an unsupported use produce a precise diagnostic or a named hole, never
    silence? (rule 12)
12. **Identity kept?** Does every entity, claim and piece of evidence it introduces have a typed
    identity of its own (subject, claim, dependencies, artifacts, checker rule, freshness), never a
    string, a display name, a first-match lookup or one status standing for several independently
    degradable claims? Does it keep apart identities that change independently (implementation,
    model, exported contract, proposition, policy, claim scope) and say which one moves under each
    change? An exact digest prevents substitution but says nothing about whether a model is
    faithful; an identity key holds the subject of a fact, never alternative answers, so
    contradictory rows (trusted and proved, refinement and equivalence) cannot coexist under
    different keys. (rule 13)
13. **Honest under hostile input?** For an evidence or tooling feature: does it treat proof
    modules, generated artifacts, receipts and checker output as adversarial, define limits,
    malformed, duplicate and surplus input behaviour, negative controls and mutation tests, and say
    how a revoked checker or assumption degrades only the claims that depend on it? Silence creates
    a missing obligation, never an assumption. (rule 12)
14. **A real benefit for audited code?** Is the gain more than writing speed? Convenience alone is
    not enough, and brevity alone never outweighs a visibility loss. (rules 4, 17)

**In one line.** A feature is promising when it makes the language and the compiler easier to
explain at the same time: explicit, local, phase-separated, summary-friendly and easy to lower
away, never implicit, global, inference-heavy, body-dependent or hard to model formally.

**Ordering.** Architecture before ornament; visibility in tooling before convenience syntax;
layout and ABI credibility before feature expansion; proof-friendly boundaries before richer
abstractions; replayable evidence alongside each new contract family. The roadmap applies this
order; it does not restate it.

**Borrowed ideas.** Copy constraints before copying features: Zig, Austral, SPARK and Odin are
most useful where they say no. [INFLUENCES.md](../legacy/docs/project/INFLUENCES.md) records what is copied, adapted and
rejected.

**Recording a refusal.** A rejected feature with its reason is worth more than a feature added
without one. A new refusal gets an entry in the next section, with its research note when there is
one. A refusal that is a language rule is an owner decision first ([decisions.md](decisions.md)).

## What Concrete refuses

Each refusal is either **Permanent**, with the reason, or **Reopens when** a named condition holds.
"Under the pull rules" means that a real workload, bug report, pilot or user need runs into the
refusal and measures its cost; a hypothetical convenience never counts (rule 17). Reopening a
refusal that is a decided language rule is an owner decision, recorded in
[decisions.md](decisions.md).

Some former "not yet" entries are planned work, not refusals, and live in the roadmap: freestanding
targets (the [allocation decision](decisions.md#decided-2026-11-02-allocation) already
covers their allocators; [R-0323](../legacy/docs/archive/roadmap-2026-11/ROADMAP_BACKLOG.md#task-r-0323) and
[R-0324](../legacy/docs/archive/roadmap-2026-11/ROADMAP_BACKLOG.md#task-r-0324) split std and its capabilities), package management
(decided 2026-10-17, in the [task register](archive/roadmap-2026-11/ROADMAP_TASKS.md)), and the richer contract layer
(dependency-flow contracts, mature loop invariant and variant authoring, the specification
library, and package and release evidence summaries, phase E of the
[roadmap](../ROADMAP.md#phases)). That layer's syntax is frozen only after a flagship or external
workload needs its facts, and its facts are reported through the one evidence ledger (rule 12).
Within that layer the decided rules hold: no `old`, quantifier or implication in contracts
([OD117](decisions.md#od117)), specification functions with a required, total body
([OD115](decisions.md#od115)) and no total-function category
([OD116](decisions.md#od116)). How frames, entry-state facts and termination are stated
inside those rules was decided on 2026-11-05 (row P18, [record](decisions.md#decided-project-contracts)): no snapshot construct, frame
and entry/exit properties as Lean theorems (a source frame clause would be a new owner decision),
and per-function termination theorems for ordinary functions.

**Hidden runtime and hidden work**

- **Garbage collection and hidden reference counting.** Permanent. They hide when memory is
  reclaimed and whether a call allocates; linear ownership and explicit cleanup replace them.
- **A hidden async runtime, executor or scheduler, and function colouring.** Permanent. They hide
  concurrency and scheduling behind calls that look ordinary.
- **Explicit structured concurrency.** Reopens when [R-0399](../legacy/docs/archive/roadmap-2026-11/ROADMAP_BACKLOG.md#task-r-0399)'s pull
  trigger holds: a workload needs concurrency after the new compiler's v1 surface is frozen. Any
  design keeps authority in `with(...)` and handles as linear values; single-threaded execution
  until then.
- **Exceptions and unwinding.** Permanent. They turn every call into a hidden exit. Recoverable
  failure is a `Result` handled by an exhaustive `match`, running out of memory included
  ([allocation decision](decisions.md#decided-2026-11-02-allocation)); an abort is terminal
  and runs no deferred call ([OD10](decisions.md#od10)).
- **Postfix `?` and any implicit error propagation or conversion.** Permanent. It hides a function
  exit, a cleanup boundary and a conversion behind one character; the error arm is written.
- **Mutable global state of any kind.** Permanent ([OD8](decisions.md#od8)). Constants are
  truly immutable; resources reach code only as values handed to it.

**Implicit conversions and inference**

- **Implicit numeric conversions.** Permanent. They hide data loss. `as` converts only when no
  value can be lost ([OD11](decisions.md#od11)); every other conversion is a named function
  ([OD99](decisions.md#od99)), and a checked one reports failure as a `Result`
  ([OD106](decisions.md#od106)).
- **Truthiness.** Permanent. A condition is a `bool`; no other value stands in for one.
- **Implicit string conversion** (`Display`/`ToString`-style hooks). Permanent. It hides
  allocation and dispatch. The reserved output and append forms ([OD133](decisions.md#od133))
  accept a closed list of types, expand to typed calls and keep their authority visible.
- **Global (Hindley–Milner) inference and inference from the expected result type.** Permanent.
  Signatures are written in full. A generic call's type arguments are inferred only from the checked
  types of its arguments ([OD46](decisions.md#od46), [OD129](decisions.md#od129));
  what no argument determines is written explicitly. Capability arguments are not inferred at all: they
  are written on every capability-polymorphic call and checked (owner revision of
  [OD45](decisions.md#od45) and [OD87](decisions.md#od87), 2026-11-05,
  [record](decisions.md#decided-2026-11-05-revisions)).

**Dispatch and abstraction**

- **Closures and anonymous functions with capture.** Permanent. Captured data and control flow are
  invisible at the call site. Named functions, capture-free function values, monomorphized generics
  and an explicit context parameter replace them ([detail](../legacy/research/language/no-closures.md)).
- **Trait objects and hidden dynamic dispatch.** Permanent. An opaque vtable hides the call target
  from the reader, the analyses and the prover. Enums, monomorphized generics and explicit function
  values replace them ([detail](../legacy/research/language/no-trait-objects.md)).
- **Implicit trait resolution beyond monomorphization.** Permanent. Traits are coherent, an
  ambiguous call is qualified, and resolution is by typed identity ([OD6](decisions.md#od6)),
  so adding an impl elsewhere cannot change what a call means.
- **Class inheritance.** Permanent. It makes the call target depend on a hierarchy instead of the
  source; structs, enums, traits and composition replace it.
- **User-defined operator overloading.** Permanent. An operator would hide allocation or effects
  behind arithmetic syntax; operators take primitive operands only
  ([OD26](decisions.md#od26), [OD42](decisions.md#od42)), and user types use named
  functions.
- **Hiding an operational capability**, for example a trusted wrapper that uses `Fs` or `Alloc`
  without declaring it. Permanent ([authority rule 5](decisions.md#decided-2026-11-02-authority)).
  A caller must see what authority a call uses. A `trusted fn` absorbs `Unsafe` only, which is a
  caller safety obligation, not authority ([TRUST-5](../legacy/docs/spec/trusted.md#TRUST-5)).
- **Umbrella capabilities and capability aliases** (`Std`, user `cap X = ...`). Permanent
  ([authority rule 6](decisions.md#decided-2026-11-02-authority),
  [audit decisions](decisions.md#decided-2026-11-02-audit)). A signature lists its real
  capabilities.
- **An effect system beyond `with(...)`** (algebraic effects and handlers). Permanent. Permissions
  are compile-time sets over a fixed, reserved list of capabilities and resources are linear values;
  that needs no runtime support and keeps signatures readable.
- **Foreign function values.** Refused ([OD4](decisions.md#od4)). Reopens when the owner
  admits typed `extern "C" fn` types, which OD4 leaves for later, with the permissions of foreign
  callbacks decided at that point ([authority rule 4](decisions.md#decided-2026-11-02-authority));
  [R-0283](../legacy/docs/archive/roadmap-2026-11/ROADMAP_BACKLOG.md#task-r-0283) reviews the C interop requirements when phase C becomes
  active or next.

**Generation and metaprogramming**

- **Source-generating macros, derive helpers and in-language source generation.** Permanent. They
  break file-local parsing and phase separation and make audit output describe code nobody wrote.
  Generics, ordinary functions and external generators whose output is reviewed as ordinary source
  replace them; attributes classify, never generate.
- **Derived structural equality.** Permanent as language machinery, for the same reason; equality
  is written or generated as reviewable source.
- **General compile-time evaluation** (`comptime`, `constexpr`-style). Reopens when a workload under
  the pull rules needs compile-time values beyond constant declarations; any design stays
  constants-only and states its interaction with the semantics.
- **Broad in-source conditional compilation** (`#[cfg]` throughout files). It hides control flow,
  authority and target assumptions behind build configuration. Target-specific code is selected by
  module and file per target profile in `Concrete.toml`, and audit output names what was selected
  and excluded. Reopens when, with the project model, target profiles and the hosted/freestanding
  std split ([R-0323](../legacy/docs/archive/roadmap-2026-11/ROADMAP_BACKLOG.md#task-r-0323)) in place, a workload under the pull rules
  shows that module and file selection is not enough; any form is narrow and appears in audit
  output.

**Calls and declarations**

- **User-defined and C-style variadic functions.** Permanent. They are unchecked or complicate
  every signature. The reserved output and append forms are the only multi-argument forms, and they
  are not a function type and cannot be passed as values.
- **Default arguments.** Permanent (owner, 2026-11-05, row P17a,
  [record](decisions.md#decided-project-refusals)), reopened only by a new owner decision. A
  call shows every argument it passes; defaults conflict with visible arguments and with one form per
  situation. General compile-time evaluation and broad conditional compilation (above) keep their
  evidence-based reopening (row P17b).
- **Lexical shadowing of a visible local, parameter or top-level name.** Permanent
  ([SCOPE-1](../legacy/docs/spec/scope.md#SCOPE-1), [OD67](decisions.md#od67)). One name, one binding
  in a scope; the compiler still never recovers identity from spellings (rule 13).

**Contracts and ghost code**

- **Decorative contracts.** Permanent. A contract is a claim that lowers to an obligation and is
  reported with its evidence; contracts never change what a program does at run time
  ([OD125](decisions.md#od125)), and a vacuous one is reported as such
  ([OD120](decisions.md#od120)).
- **`old`, quantifiers and implication in contracts.** Permanent ([OD117](decisions.md#od117)).
  Such properties are stated as Lean theorems, keeping the contract language small.
- **Ghost code that affects execution.** Permanent. Ghost code itself is admitted as decided:
  `ghost let` with `ghost` reserved ([OD81](decisions.md#od81)) and specification

<a id="decided-2026-11-05-revisions"></a>**Owner-approved revisions of recorded rules** (each also noted at the rule it revises):

- **OD45 and OD87** (rows Q5.1, Q5.4): capability arguments are written explicitly at every polymorphic call and checked against the callee; there is no capability inference and no inference solver. OD46 (type arguments from checked argument types) is unchanged.
- **TYPE-22@1's examples** (row Q6.4): a constant whose initializer provably fails is refused at compile time whether or not it is used (OD118); both examples, `unused-constant-never-runs` and `constant-traps-at-use`, become reject examples. When a constant is evaluated (at each use, never at start) is unchanged.
- **TRAIT-1@1** (row Q2.8): two impls with equal heads may coexist only when Copy/Destroy disjointness (OD28) makes their domains disjoint, as in `impl<T: Copy> Destroy for Vec<T, A>` beside `impl<T: Destroy> Destroy for Vec<T, A>`. No other coherence or orphan rule changes, and no disjunctive bound syntax is added.
- **The generated-chapter requirement** (rows Q9.15, P3): Lean is the specification, in one main normative file with doc comments and examples; no prose is generated from it. This confirms the [2026-11-04 decision](#decided-project-lean-is-the-spec). The "one main normative file" wording is revised 2026-11-06 by the [long-term changes](#decided-project-long-term-2026-11-06): one authoritative specification library in cohesive modules, with `ConcreteSpec/Spec.lean` as its public import.
- **Authority rules 13, 5 and 7** (row Q7.11): `Console` joins the reserved capability set, for operations on the `StdIn`, `StdOut` and `StdErr` grants; rule 5's operational list and rule 7's primitive table include it. `Device` stays for device grants.
- **The text-only slice of R4 F4.3** (row Q4.7) is replaced before it was recorded: one scoped form opens every view, `borrow [mut] source [from a until b] as view { … } [else { … }]`. Without `else` an invalid range traps, like indexing; with `else` it is handled; a proven invalid range without `else` is refused (OD118). Arrays need `a ≤ b ≤ len`; text also needs UTF-8 scalar boundaries at both byte offsets.
- <a id="decided-2026-11-05-q6-2-fields"></a>**Q6.2 and R4 F12, known values through structs** (owner-approved revision, 2026-11-05, made during A2b): known values propagate field by field through immutable struct construction and destructuring. The checker tracks an abstract value for each binding: unknown, a known scalar, or a constructor whose fields carry their own abstract values. Constructing a struct records each field's fact independently; an immutable binding keeps the fact; destructuring hands each field's fact, recursively, to the corresponding immutable binder; an unknown component stays unknown without discarding its known siblings; an ownership transfer keeps the facts for the receiving binding without permitting reuse of the consumed one. Q6.2's exclusions stay (mutable state, branches and paths, user-function calls, calls outside the table, elaborator temporaries). So `let S { a } = S { a: 200u8 }; a + 100` is refused, in trusted and unreachable code too (OD118 as revised by Q6.4). Before this revision a field bound by destructuring was not known and that program was accepted and trapped.
- <a id="decided-2026-11-05-q9-1-reads"></a>**Q9.1, read forms** (owner-confirmed, 2026-11-05): `copy x` is allowed only when `x` has a Copy type and `move x` only when it has a non-Copy (linear) type. Each read has one form; `move` of a Copy value and `copy` of a linear value are both refused.

<a id="decided-2026-11-05-new-rules"></a>**New rules** (P4): duplicate variant names in one enum and duplicate method names in one impl are refused, like duplicate fields (bug 313); the rule gets its ID and diagnostic when it is written in Lean.

<a id="decided-2026-11-05-core"></a>**Core rows** (the answer is the row's recommendation):

- **Q1.1** What is an allocator brand? — Separate erased `Brand` kind.

- **Q1.3** How are packages formed and opened? — Explicit pack; lexical unpack; repackage escapes.
- **Q1.4** How are brands compared and supplied? — Nominal brand equality; explicit brand arguments.
- **Q1.5** How are allocator dependencies tracked across calls? — Structural dependencies; checked interface summaries.

## Q1. Does the front end keep reporting after its first failure? (audit U6)

**Legacy.** `--diagnostics-json` ran an error-tolerant front end (Phase 4 #12a). A pass that failed
did not hide the diagnostics of passes that could still run, and the result carried a `partial`
flag. **New.** The checker returns `refused (rs : List Refusal)`, every refusal it finds, in a
deterministic order (SPEC_UNIFICATION, the checker result). For the lexer, parser and elaborator,
nothing is decided.

- **(a)** Stop at the first lexer, parser or elaboration refusal. The checker still reports all of
  its own refusals.
- **(b)** Recover in a defined way inside each stage: the lexer skips to the next token, the parser
  resynchronizes at a statement or item boundary, and elaboration continues over the items that
  resolved. Every refusal is reported, and the result is marked incomplete when a later stage could
  not run. Recovery is part of each stage's specification, so it is proved like the rest of the
  stage.
- **(c)** Like (a), but run every independent unit (file, later module) separately, so one broken
  file does not hide another's refusals. There is no recovery inside a unit.
- **(d)** Recover only in an unverified diagnostics-only path, as legacy did, with the proved path
  stopping at the first refusal.

**Recommendation: (c) now, and (b) for the parser when a workload shows that one refusal per file
is too slow to fix.** (c) gives agents and people every independent refusal without making
recovery part of the proved front end. (d) is a second front end, which the one-form rule refuses.
(b) adds proof work to the LL(1) parser now for a convenience.

## Q2. An exit-code scheme for `build`, `facts` and `diff`, and a check-only mode

**Legacy.** One taxonomy (`legacy/Main.lean` 7–29): 0 success, 1 usage, 2 obligations missing,
3 stale evidence, 4 proof-check failure, 5 solver failure, 6 internal error. It was not applied
everywhere: `concrete check` exited 1 on any issue, and `diff` exited 1 on a weakened fact and 2 on
incomparable snapshots. **New.** R-0479 and the policy results above; no numbers are decided.

- **(a)** One small taxonomy for every command, from the typed result: 0 accepted or satisfied,
  1 refused (a program refusal, a violated policy, a weakened fact in `diff`), 2 incomplete (an
  unknown fact, an analysis limit, an incomparable snapshot or schema version), 3 usage, 4 internal
  or toolchain failure. The JSON record gives the detail. It is generated from one Lean definition,
  as legacy's help block was.
- **(b)** A finer taxonomy like legacy's, one code per cause (refused, policy violated, proof
  missing, proof rejected, incomplete, usage, internal, toolchain).
- **(c)** 0 or 1 only; the JSON record gives every reason.
- **Check-only mode.** (i) `concrete facts` gets the taxonomy and is the check, with no separate
  command; (ii) `concrete check` runs admission, the facts and the policies without code
  generation; (iii) `concrete build --no-emit`.

**Recommendation: (a) with (i).** (a) keeps the decided three-valued policy result (satisfied,
violated, incomplete) visible to CI without parsing, and keeps internal failures apart from
refusals. (b) duplicates in numbers what the record already says. (c) loses "incomplete", which the
facts design says must never read as a pass. For the check, (i) avoids a second command that does
what `facts` already does. Artifact facts such as the stack bound need a build, so `facts` reports
them "not established" when no artifact exists.

## Q3. The `trace`, `emit`, `run`, `interp` and `help` commands

**Legacy.** `--trace-pipeline` named the first failing stage; `--emit-core`, `--emit-ssa` and
`--emit-llvm` printed an IR; `run [-- args]` built and ran; `--interp [-- args]` ran the reference
interpreter; `--help`, `help` and `-h` printed grouped help. **New.** Slice 0's `Output` keeps every
intermediate, the Lean evaluator is the reference interpreter (R-0496, the I/O driver R-0586), and
none of these commands is named.

- **(a)** All five as subcommands: `concrete trace`, `concrete emit --stage <core|mir|mem|bir|llvm|lcb>`,
  `concrete run`, `concrete interp`, `concrete help`.
- **(b)** Fold the inspection into the two commands that exist: `concrete build --emit <stage>` and
  `concrete facts --trace`; add `concrete run` and `concrete help`. The evaluator runs only in CI's
  differential.
- **(c)** Add `help` now and nothing else until a slice needs it; `trace` and `emit` stay developer
  scripts.
- **(d)** Like (a), but `interp` is `concrete run --evaluator`, one command with two engines.
- **(e)** (a) without `run`: `trace`, `emit`, `interp` and `help`, each scheduled with its data
  (`help` first, `emit` with the IR printers, `interp` with the evaluator's I/O driver), and `run`
  decided at slice 1, when the launcher exists.

Every option except (c) extends the decided two-command slice-0 surface, so each is an owner
decision.

**Recommendation: (e).** Each answers one question and maps to one data source
(the stage registry, one IR, the evaluator, the command table), which is the most transparent.
(d) merges two different meanings (the native build and the Lean semantics) under one name. (b)
hides a question behind a flag on a command that answers another. `run` adds nothing that
`build` plus executing the file does not do.

## Q4. The formatter's `--check`, `--write` and `--stdin` modes (slice 17)

**Legacy.** `concrete fmt FILE` printed to stdout, `--check` exited nonzero when the file was not
formatted, `--write` rewrote the file, and `--stdin` formatted standard input. A file is formatted
when formatting its parse gives the same bytes back.

- **(a)** All three, with legacy's meaning and the Q2 exit codes.
- **(b)** `--check` and `--write` only; editors pipe a temporary file.
- **(c)** `--check` only, as a CI gate; the formatter otherwise prints to stdout.
- **(d)** A canonical form that is part of admission: an unformatted file is refused.

**Recommendation: (a).** `--check` is the CI gate, `--write` is the daily use and `--stdin` is what
editors and agents need without touching files. (d) makes layout a language rule, which no decided
row asks for and which would refuse correct programs for whitespace.

## Q5. Agent feature discovery

**Legacy.** `concrete prove --capabilities` printed a JSON object of supported features, obligation
kinds, evidence classes and the schema version; `--schema` printed the JSON schema; `--help=agent`
printed a workflow guide. **New.** The JSON schema is generated from the Lean types (R-0593); every
output carries `spec_version`; nothing lists features.

- **(a)** `concrete schema` prints the generated JSON schema of diagnostics and facts, and
  `concrete capabilities` prints the supported slice, the commands, the fact kinds, the rule IDs and
  the versions, all generated from the Lean registries.
- **(b)** Only `concrete schema`; feature support is read from the schema and the slice number.
- **(c)** Nothing on the CLI; the schema and the rule registry are published files.
- **(d)** (a) plus a workflow guide for agents, like `--help=agent`.

**Recommendation: (a).** An agent should learn what this exact compiler supports from the compiler,
generated from the same registries, so the answer cannot drift. (d)'s guide is prose that goes
stale; the next actions in each diagnostic (R-0479) already say what to do.

## Q6. A proof-floor policy for user contracts (from slice 8)

**Legacy.** Policy `require-proofs` refused a project with any eligible function whose proof was
missing, stale or blocked. **New.** Safety obligations cannot be left open: admission refuses them
(no hidden traps). A user's own contract (an `#[ensures]` or a stated property) may be "not
established" and is then reported as a fact; no policy key requires it.

- **(a)** A policy key in `Concrete.toml` `[policy]`, for example `require-contract-proofs`, scoped
  like the predictable policy (project or module, tighten only, transitive to dependencies): every
  stated contract in scope must be established; conditional on named premises passes only if the
  policy lists them.
- **(b)** No key: an unproved `#[ensures]` is refused at admission, as safety obligations are.
- **(c)** No key: the facts report the gap and CI checks the JSON itself.
- **(d)** (a), plus a strength floor: a point-instance proof does not satisfy it (R-0585 strength
  labels).

**Recommendation: (d).** It is a policy over existing facts, as the facts and Concrete.toml rows
require, and it uses the strength labels so that a single-input proof cannot pass a floor meant for
a contract. (b) changes what a contract means, and an unproved contract is legitimate during
development. (c) makes every project re-implement the same check outside the compiler.
